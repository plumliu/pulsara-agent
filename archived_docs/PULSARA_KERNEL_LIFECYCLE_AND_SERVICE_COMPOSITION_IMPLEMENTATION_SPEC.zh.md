# Pulsara 内核生命周期与服务组装实施规格

状态：已实施，本机验收完成。日期：2026-11-03。

## 1. 目标与边界

由 `KernelHostCore` 完整拥有内核运行所需的资源、定时任务服务及会话执行生命周期。桌面层消费同一套服务，负责界面和宿主交互，不能靠创建后回填来补齐内核能力。

本规格处理冷资源初始化与关闭、会话注册后激活、定时任务归属和桌面依赖一致性。MCP 网络就绪与 native/META 选择遵循 [MCP 首次请求就绪规格](PULSARA_MCP_FIRST_REQUEST_READINESS_IMPLEMENTATION_SPEC.zh.md)，不在本规格复制等待逻辑。

同一 epoch 的 SYSTEM/tools 字节不变、messages 只追加；只有现有 cold epoch 和显式采纳的 compaction successor 可以重建根。修复组装问题不得给已有 epoch 临时加工具，也不得制造新的 rebase 边界。

## 2. 实施范围与验收依据

| 合同 | 生产入口与验收重点 |
|---|---|
| 完整内核工具组装 | `KernelHostCore` 在封存 ROOT 工具前提供真实定时任务服务；裸 Core 与桌面使用同一路径 |
| 唯一冷资源初始化 | 并发准备加入同一操作，中间资源局部持有，成功一次发布，失败清理完成后才允许重试 |
| 关闭后不可复活 | 关闭封住新准入，汇合已接受工作，原 Core 不再创建或发布新资源 |
| 注册后激活 | 构造只组装，Core 注册后启用消费者；pending 输入在实际 cold 准备边界等待 MCP |
| 同源桌面依赖 | settings、catalog、runtime 和 Core 使用同组实际 owner，冲突注入拒绝 |
| 独立关闭与数据保留 | 一个关闭失败不跳过其他独立 owner；必要结算与可丢弃收尾分别判断 |

Memory、Skill、MCP、Code Mode、子代理、会话查询和终端仍使用现有组装与权限边界。行为验收覆盖真实队列、数据库、provider 请求和本地子进程，不以工具数量或 fake 返回值替代物理完成事实。

## 3. 所有权合同

| 对象／行为 | 唯一负责方 | 桌面职责 |
|---|---|---|
| 数据库访问 lease、repository、历史维护、blob GC 及其 IO | Core | 请求准备／读取，展示状态 |
| 会话打开、恢复、执行准入、关闭与隔离 | Core 的现有生命周期机制 | 保存界面 handle、选择会话和展示；委托同一执行 owner |
| 定时任务读写、到期投递、唤醒与关闭 | Core 持有的 `ScheduledTaskService` | 页面查询、编辑及 Run once 调用同一服务 |
| 单会话工具及其执行依赖 | Session 在注册前完成组装 | 不通过后填字段补工具 |
| MCP attempt、连接候选、物理清理 | 现有 supervisor | 展示连接／失败状态 |
| cold-epoch 首次 MCP 等待 | 现有执行准备边界 | 展示进度和发送停止请求 |
| settings → catalog／runtime → Core 的一致依赖链 | 唯一组装入口 | 复用已确定的同一组 owner |

不新增另一套会话注册表或调度器。若桌面控制器现有的同会话去重、恢复 reservation、关闭隔离承担内核必要语义，应将该执行职责归入现有 Core 生命周期链；桌面仍可持有 UI 映射，但不能独立决定第二套执行状态。

## 4. 冷资源初始化与关闭

### 4.1 单次初始化操作

- Core 持有一个进程内初始化操作。并发 `prepare_resources()`、打开／恢复会话、记忆管理及历史读取加入同一次操作。
- 在 Core 的短临界区中完成初始化准入与操作归属；不持锁跨数据库验证或网络／物理 IO。
- lease、repository、历史维护和 GC 的中间结果由初始化操作局部持有。完整成功后一次发布，失败或取消则清理已取得的资源，不能留下半组装字段。
- 一个等待者取消只取消自己的等待，不能取消其他等待者仍在使用的初始化。Core 关闭负责与该物理操作汇合。
- 一次初始化失败后，只有它的物理清理已完成、Core 仍开放时，后续正常调用才可以重新尝试；不保留不完整资源，不新增自动重试预算或总次数限制。
- 没有真实已准入会话工作时，初始化后台 owner 不得抢先启动会话执行。

### 4.2 关闭准入与在途操作

- 关闭开始后，拒绝新的资源准备和数据库操作，返回既有关闭类结果；只读请求也不能绕过。不得通过 `_repository is None` 推断可以重开。
- 已受理的初始化和资源使用操作必须交由各自现有 owner 结束，Core 等待其物理完成后才能释放仍被使用的共享资源。复用已有 lease、IO 和关闭机制，不建立新的逐请求持久记录。
- `shutdown()` 的并发调用与等待者取消继续加入同一关闭操作。关闭结果按第 8 节区分物理完成、可丢弃收尾错误和未确认执行；不能因可丢弃错误阻断其余关闭。
- 成功关闭后的同一 Core 永久不可重新激活。需要新运行实例时由正常组装入口创建新 Core，而不是清空状态字段再次初始化。
- HTTP 在 draining 时停止接受使用内核数据资源的新请求，包括数据 GET；允许保留健康检查和已有必要关闭观察。Core 本身必须拒绝新操作，不能只依靠 HTTP 拦截。

## 5. 会话组装、注册与激活

执行顺序固定为：

```text
Core 受理打开／恢复 → 完整组装 Session → 启动 MCP 后台连接
                  → 注册 Host／执行路由 → 启用队列消费者
                  → 执行输入 → cold 准备边界等待 MCP → 冻结并请求
```

- Session 构造不能立即启动可消费 canonical 输入的执行循环。由 Core 在完整组装和注册后明确激活；必要的 writer 续租可以在准备期间维持。
- 打开和恢复会话不等待 MCP 网络就绪。启动 MCP 是安排既有后台工作；不能恢复服务级 required 等待。
- 普通 pending 输入、定时输入和子代理队列均经过同一注册／激活边界；已有输入保留原 canonical 身份和顺序，不复制成新指令。
- 注册前任何协作组件提供的 wake 只能保留为已有进程内唤醒事实，不得越过激活边界触发模型执行。检查其他可能触发执行的构造期后台循环，不能只移动一个 `_queue_wake.set()`。
- 打开失败、关闭获胜或所有权失效时，未激活的 Session 仍由原打开操作清理，不产生 provider 请求；已注册但未完成激活的失败不能留下可执行的孤儿 Host。
- 关闭仍回收未启动或已启动的各类 owner，不因任务尚未创建而跳过其他清理。

本节解决“何时允许执行”，MCP 规格解决“何时允许首次冻结”。不引入数据库 ready 标记、第二套屏障服务或工具列表动态修补。

## 6. 定时任务完整归入 Core

### 6.1 组装与生命周期

- `KernelHostCore.production()` 创建并持有完整定时任务服务；所有新 ROOT Session 在封存内置工具前取得同一服务。删除 `core.scheduled_tasks = ...` 的桌面回填路径，以及因未接入服务而静默缺两个工具的分支。
- 服务创建不等于立即扫描或投递。具备已验证数据库资源、既有可用模型配置／目录并完成当前运行所需初始化后，由 Core 的明确运行准入启动；外层入口可以请求准备或通知配置变化，但不能直接另起服务循环。
- 模型目录恢复、数据库准备、设置变更通过现有事实和唤醒路径影响同一服务。保留原来不可用时等待、修复后继续的行为。
- Core 关闭先停止服务的新投递，同时开始停止现有会话及本地进程；按原接纳／结算机制汇合已经受理的物理工作，确认依赖不再使用后释放共享资源。不能先等待一个阻塞的调度工作，再开始停止其他独立会话。桌面不再独立拥有该服务的关闭职责。
- 数据库重置继续由现有显式重置流程协调，先停止所有使用者；重置后复用或重建 Core 遵循现有 restart-required 产品语义，不能使已关闭 Core 复活。

### 6.2 保留必要执行语义

服务不再依赖 `LocalSessionController`，但下列功能全部保留：

- 根据明确 session ID 恢复目标会话；复用 Core 的并发打开／恢复与关闭隔离，不能重复取得 writer 或绕过忙碌状态。
- 修改计划前定位同一个真实 live Host；已有写入 reservation、权限和事务检查继续有效，无 live Host 的管理不强行打开会话。
- 定时输入通过现有 `submit_prompt`／队列 admission 进入执行，保留原计划 revision、去重、投递顺序、权限收窄和副作用结算；不能直接调用模型或模拟用户消息。
- 用户级计划页面在没有活动会话时仍可读取和管理；显式操作选定会话时保留该目标。用户／memory domain 由既有明确身份输入提供，不从当前 UI 会话推导，也不扩展跨域访问。
- Run once 继续是现有 UI 产品操作；不因服务迁移而新增模型执行计划的 action。计划一次性／重复、暂停／恢复、切换、删除及已排队工作的语义不变。

### 6.3 工具与正常运行验收

裸 production Core 和桌面运行通过同一能力组装链。现有 ROOT bypass-permissions 条件下的完整内置目录为 36 个，包含 `query_schedules` 和 `manage_schedule`。子代理、其他权限、模型 schema 兼容性和预算选择继续按既有合同，不把“所有场景都必须暴露 36 个”作为新规则。

核心验收是两个工具具备真实执行服务、能正常查询和修改，而不是只锁定数量。构造完成后再注入服务、修改已封存绑定或改写同 epoch 原生数组均不接受。

## 7. 桌面依赖一致性

`DesktopApplication` 不能独立补出与已传入执行 owner 不同的 settings、catalog 或 runtime。

- 未传入上层 owner 时，按现有依赖顺序创建一套 settings、catalog、runtime 和 Core。
- 传入 Core 时，从该 Core 取得实际 runtime 及其 settings、catalog；传入 runtime 时，使用它已有的 settings、catalog，再构建 Core。
- 同时显式提供的依赖必须是同一组实际 owner；冲突在构造阶段明确拒绝，不能按配置内容相等就视为同一 owner，不能静默选一边。
- HTTP、模型管理、实际执行和 credential scrub 使用这条链上的同一组对象。提供必要的只读属性即可，不建立新的服务容器或 owner 注册表。
- 保留既有宿主回调与测试注入需求；适配器消费接口可以与具体对象不同，但必须有明确的同源组装，不能凭包装器类型或内容相等推断一致。

## 8. 关闭体验、丢弃边界与失败语义

### 8.1 用户先离开，现有 owner 完成收尾

- 用户通过现有会话关闭操作请求停止并关闭时，界面立即离开该会话，返回现有列表或其他页面。保留已保存的会话历史；这不是删除会话或修改计划的操作。普通浏览标签切换／关闭不因此获得停止会话的额外语义。
- 前端入口为会话“更多操作”中的“停止并关闭会话”，复用 `/api/sessions/{session_id}/close`。后端封住该会话新执行并接受现有关闭 owner 后返回 202，不等待完整物理收尾；离开页面和稍后到达的关闭响应只能释放原连接，不能影响用户已切换到的另一会话。
- Core 立即停止该会话的新执行准入，后台继续完成现有关闭操作。页面离开、请求断开或等待者取消，均不丢失真正的关闭 owner。
- 一个会话关闭报错后，继续尝试关闭其他独立会话。按现有 ROOT／子代理依赖顺序处理，不能把仍有依赖的资源当作独立资源提前释放。
- 临时内容和非必要收尾错误不弹模态框、不要求用户确认，也不使页面停留等待。细节进入现有日志；不向聊天插入清理过程，不增加灰色解释文字。
- 确有执行未停止时，在既有会话状态／通知入口给出简短事实，例如“任务仍在停止”。用户再次打开时不得创建第二个执行 owner；可以查看已保存历史，但恢复执行必须等待旧执行确认停止。
- 若只能通过重启整个运行时解除未停止工作，提供明确的“重启工作台”操作，说明会中断其他运行任务。单个会话关闭不能自动重启整个工作台；重启不删除用户数据，也不自动重做结果不明的操作。

### 8.2 可以丢弃与必须保留的内容

| 内容 | 关闭时处理 |
|---|---|
| 尚未 canonical 接受的流式回复尾部、思考及展示增量 | 可以丢弃；不能把不完整尾部伪装成完整回答，也不为保存它额外调用模型 |
| 进程内进度、临时预览、可重建缓存和派生投影 | 可以丢弃；不为关闭建立持久快照 |
| 未发布、未接受且没有用户文件归属的临时中间输出 | 可以丢弃；已被接受结果引用的正文、blob 或媒体按其现有保存／GC 规则处理 |
| 临时连接及已停止工作的本地句柄 | 关闭并释放；释放句柄不等于已经停止其背后的工作 |
| 非必要 SessionEnd Hook 输出及清理诊断 | 不要求持久保存；已有日志按原保留策略记录，不因保存这些输出延迟退出。已启动 Hook 的真实执行仍须停止／收尾 |
| 已接受的用户消息、排队输入、回复、工具请求及工具结果 | 保留 canonical 记录及原顺序；关闭不能删除、复制或改写成成功，队列取消／恢复按既有合同执行 |
| 已发生或正在结算的工具副作用 | 保留已有结果与必要结算事实；不能当作临时文本丢弃，不能因为收不到返回值就推断未发生 |
| 已保存的计划、设置、凭据和权限配置 | 保留；关闭不暂停／删除计划或重置配置。应用退出后停止本次运行的调度，后续启动仍按现有计划规则处理 |
| 用户文件、已发布交付物和外部操作结果 | 保留；不能按临时目录或中间产物的表面路径猜测可删除性 |

“可以丢弃未接受输出”只覆盖展示和内容保存，不授权跳过工具副作用结算或提前关闭其数据库依赖。复用现有接受／结果／未确认语义；不得新增一套关闭收据或恢复日志。若故障导致无法写入最终状态，保留最后已经确认的记录和可取得的诊断，不伪造补写成功。

### 8.3 根据物理完成事实决定结果

下表是处理规则，不要求增加新的持久状态或状态注册表。

| 已有 owner 能证明的事实 | 产品与资源处理 |
|---|---|
| 执行和必要结算均已结束，临时资源已释放 | 关闭完成 |
| 工作最终已退出并完成必要结算，但超过既有关闭看门狗时间，或可丢弃收尾报错 | 仍视为已关闭，记录诊断；不能只因异常类型为 TimeoutError 就长期隔离 |
| 物理工作已退出，但必要 canonical 结算失败或提交结果不明 | 可释放确认不再使用的物理资源；保留未完成／未确认事实，不宣称任务成功或结算完整，不自动重放副作用 |
| 本地或远端工作是否停止尚不能确认 | 停止新准入，保留必要 owner 和仍被使用的共享依赖；继续其他独立关闭，不伪装全清理成功 |

一个普通 `close()` 异常本身既不能证明“工作仍活着”，也不能证明“已停止”。应使用现有物理 join、事务结算及 ownership 事实判断；不新建探测框架，不无限重试关闭操作。

### 8.4 终止升级与退出应用

- 先请求正常停止，并完成已受理工作的必要结算；达到既有关闭看门狗边界后，按现有进程 owner 的终止机制升级，停止 Pulsara 明确拥有的本地工作进程并确认退出。只取消 asyncio waiter 或删除引用不算终止。
- 不新增首轮／会话／应用总运行时限或任意重试次数；本节复用已有关闭期限。物理 join 在看门狗后继续汇合时，不扣住用户的会话页面，也不能在异常返回后遗失 owner。
- 无法单独终止的本地工作，由现有运行时／宿主进程边界处理；普通会话关闭走第 8.1 节明确的重启操作。用户明确退出整个应用时，可终止当前运行实例以丢弃剩余临时状态，不要求为临时输出保活整个工作台。
- 整应用退出在必要持久数据收尾后结束本次运行；若物理故障使结算无法确认，允许退出并保留已确认的数据和未确认事实，不承诺无损保存尚未接受的尾部。不能以“退出成功”暗示远端副作用已取消或执行任务已成功。
- 终止权限仅覆盖已经验证归属的当前应用运行实例及其本地工作进程，不按 PID 猜测，不终止外部服务或仍被其他 owner 使用的数据库进程。远端请求只按协议尝试取消／关闭本地连接；断开连接不能证明远端操作撤销。
- “本地子进程已停止”的事实必须包括终端、Code Mode、MCP／Hook、文件搜索的 rg 和截图的 Python／Playwright／Chromium，以及在途 spawn；空进程集合不能证明尚未返回的启动操作已完成。封新准入后复用各 owner 的实际 join；纯 HTTP 等待或进程内数据库线程不能被误当作仍有本地子进程。
- 明确 Quit／Restart 的桌面私有控制消息使用 `shutdown-workbench`，允许按上述边界丢弃当前运行实例；数据库重置继续使用严格 `shutdown`。运行时自身退出，宿主等待实际 child 退出和既有 Linux lifetime lock 后才重新启动，不终止 WSL carrier 冒充 Linux 工作退出。可使用真实会话、初始化或已受理数据操作的原有 deadline，不从请求退出的时刻另设一个应用总时限。
- 结果未知时不自动重试发邮件、修改文件、提交远端任务等操作。已有明确被接受、尚未执行的队列输入仍按原规则恢复；不能把一个可能已执行的调用重新包装成 pending 输入。
- 数据库重置或会话删除仍要求它们各自既有的关闭与权限合同。本节允许丢弃临时内容，不授权在旧工作仍可能访问数据时重置／删除数据库，也不把该失败转成成功。

### 8.5 关闭协调与实施边界

继续使用同一个进程内关闭操作；将独立资源的关闭错误收集后再判断总体结果，避免首个错误直接跳过其他独立会话。只保留尚有执行／结算依赖的共享资源；确认物理完成后的可丢弃错误不得继续占用隔离槽或阻止正常重开。

页面关闭、执行停止、必要结算、资源释放分别使用现有 owner 的实际完成事实，不靠单一抛错／未抛错判断全部结果。关闭结束后的 Core 不重新激活，重启通过正常组装创建新实例。

不引入持久清理任务、自动恢复图、轮询保活服务、第二套关闭管理器或逐项清理收据。必要错误和“不确定是否执行”继续使用现有结果与诊断通道。

## 10. 验证与实施顺序

使用仓库 `.venv`，先做确定性并发测试，再做真实数据库和必要真实模型验收。不得用 sleep 猜时序、放宽断言或新增 skip／xfail；只冻结旧结构的测试删除，其中真实权限、取消、结算和前缀行为保留。

必须覆盖：

1. 并发公开资源准备／冷读／打开只创建一套共享 owner；取消一个等待者不影响其他等待者。失败与中途关闭回收每个已取得资源，剩余 lease、GC task、IO owner 为零；失败清理完成后才能重试。
2. 关闭与冷初始化竞态不发布失去归属的资源；成功关闭后 prepare、数据读取和打开均拒绝新工作。并发 shutdown 及调用者取消保留真实结果，不重开资源。
3. Session 注册前 pending 输入不能触发执行；注册后队列顺序及 writer 身份正确，打开失败和关闭竞态没有请求泄漏。与 MCP 规格第 7 节的 pending 用例交叉证明首次冻结等待。
4. 裸 production ROOT 和桌面 ROOT 都具备可执行的两个计划工具；无活动 UI 会话时，用户级查询／管理和到期投递仍按明确 domain 正常工作。不能以注入假 scheduler 后工具数量正确替代。
5. 真实数据库覆盖计划创建、更新、切换、暂停／恢复、删除、Run once 与到期投递；保留忙碌／关闭隔离、权限、revision 冲突、一次性退役和取消后结算，无重复恢复、重复 writer 或重复投递。
6. 先构造 Core／runtime 的桌面入口复用同一依赖链；显式冲突构造失败；设置读取、模型目录、实际执行使用同一 owner。默认生产入口和现有合法注入均覆盖。
7. 真实模型通过正常完整组装运行，记录同一最终请求的工具名／数量、v3 分项与 provider usage；ROOT bypass 基线包括 36 个内置工具，MCP 分开统计。继续核对同 epoch SYSTEM/tools 字节不变、messages 只追加；不把独立实验误当同一 agent loop。
8. 调度器停止先于共享资源释放；会话页面立即离开而真实关闭 owner 继续收尾。关闭 A 的 MCP／终端报错时，独立会话 B 仍执行关闭；仍被 A 使用的共享依赖不提前释放。
9. 资源已确认退出、必要结算完成而仅有看门狗超期或非必要 Hook 输出失败时，关闭完成并保留诊断，不长期隔离、不弹确认框；物理完成但 canonical 结算未知时不混同于完整成功。
10. 可丢弃的回复尾部、进度与临时产物不阻止关闭；已接受消息／结果、排队输入、配置、计划和用户文件保持原语义。通过已提交工具副作用但返回丢失的用例证明不自动重复执行，不伪造成功或取消。
11. 未确认退出时禁止同会话双 owner，停止其他独立会话不受阻。验证仅终止真实归属进程、必要时显式重启及整应用退出；不杀外部服务，不让临时输出保活工作台。重启后保留已确认历史，未知结果不触发副作用重放，数据库重置仍受既有安全关闭前提约束。

真实验收读取现有保存配置，通过只读设置注入和已验证的独立本地测试数据库隔离；不修改生产设置，不输出凭据。保留确切输入、输出及失败证据，验证临时数据库与后台 owner 清理。

实施顺序：先按第 4、8 节统一资源准入、关闭结果与收尾所有权并修复冷资源问题，再修正注册后激活；与 MCP 规格共同验收 pending 输入；随后完成 scheduler 归属和桌面同源依赖，最后做全链路验收。关闭展示与后台收尾共用现有 owner，不通过旧路径兼容或新清理系统实现。

代码及测试按本规格实施并逐条验收；构建安装和实际配置变更由对应后续操作执行。

## 11. 实施与验收结果
