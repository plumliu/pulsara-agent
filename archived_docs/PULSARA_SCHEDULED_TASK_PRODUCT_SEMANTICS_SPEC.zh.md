# 定时计划、运行一次与计划切换的产品语义

日期：2026-10-13。

本文件记录用户确认的产品决定，是下列语义的现行权威：暂停、运行一次、恢复、一次性计划自动移除、唯一活跃计划、会话筛选、开关切换与模型指引。与 [原定时任务规格](PULSARA_SCHEDULED_TASKS_HARD_CUT_IMPLEMENTATION_SPEC.zh.md) 冲突时，以本文件为准；原规格的调度算法、权限、队列、事务与 provider 前缀连续性约束继续适用。

交付范围：已实现可信触发来源贯通、一次性计划成功入队后自动移除、原子切换，以及相应 SYSTEM、工具描述、请求包装和 UI。以 clean-v0 与 Protocol v3 同批硬切，不保留旧来源格式或计划级 COMPLETED 状态。RUN_ONCE 仅由定时任务页的用户操作产生；模型收到立即执行请求时在当前轮完成工作。代码交付不等于替换已运行服务或重建用户数据库；既有在线 epoch 不改写。

## 1. 问题与已核实事实

本地会话 `session:5e910ea311ad4c8db75dbe47926140c4` 中，用户在 2026-10-13 00:10（Asia/Shanghai）说“好，帮我停掉吧”。模型成功暂停“每10分钟问好”，任务变为 PAUSED、revision 2、next_run_at NULL。00:22 用户点击“立即运行”，既有命令记录的 kind 为 RUN_SCHEDULED_TASK，生成一次普通会话输入。

模型随后调用 get/list，发现任务仍暂停，拒绝执行 echo，并建议删除任务，因为它推断暂停失效。该推断不成立：当时实现已明确允许 PAUSED 的 run_now；此次记录是手动动作，不能作为自动定时器越过暂停的证据。

修订前 ScheduledAdmission 区分 manual/timer，但 ScheduledProvenance 只携带 task_id、task_revision、due_at_utc。模型输入统一称为 runtime scheduled trigger，并强调不是新真人消息、后续人工限制有效。工具发起的 run_now 和用户点击也未在模型来源中区分。产品动作、模型可见事实和解释规则没有对齐。

## 2. 三个独立事实

1. **计划配置**：任务何时可以自动提交输入。状态仅为 ACTIVE / PAUSED；一次性计划成功入队后移除配置。
2. **本次输入**：由自动到点或用户点击运行一次产生，是否已接受、排队或消费。
3. **实际执行**：普通会话中的工具调用、回复、失败或中断。输入被接受、一次性计划自动移除，都不保证业务目标成功。普通 turn 的 COMPLETED 仍属于执行事实，不与计划状态混为一谈。

是否接受一次请求由 runtime 的确定规则和权限入口决定。模型根据可信来源、保存提示词、会话中的有效限制执行工作；不根据当前任务状态重新猜测本次输入是否合法。任务状态不是工具操作的额外授权。

## 3. 操作语义

| 操作 | 自动计划 | 待运行输入 | 正在执行的回复 |
|---|---|---|---|
| 创建计划 | status 未填或 null 时为 PAUSED、next 为空；显式 ACTIVE 才启用 | 不立即新增输入 | 不改变当前回复 |
| 暂停计划 | ACTIVE → PAUSED，清空 next；不删除配置 | 取消本任务尚未消费的项，包括先前接受的单次运行 | 继续；需要停止时使用普通会话停止入口 |
| 运行一次 | 存在的 ACTIVE / PAUSED 均允许；周期计划的 status、revision、next 不因本操作改变；once 成功入队后自动移除 | 本任务已有 PENDING 或 RUNNING 时复用原输入；否则通过普通准入新增 NEW_TURN | 本任务正在执行时不追加；其他回复不打断、不抢占 |
| 恢复计划 | 周期计划从恢复时刻求下一个未来时点；不补暂停期间次数 | 不重建被暂停取消的输入 | 不改变当前回复 |
| 停止回复 | 不改变计划 | 沿普通会话规则，不推定取消其他项 | 通过原执行 owner 停止目标回复 |
| 删除计划 | 删除配置 | 取消本任务 PENDING | 继续；会话与已有历史保留 |
| once 成功入队后自动移除 | 同事务移除一次性配置、释放 ACTIVE 名额 | 保留刚接受或合并的输入，不取消 | 继续，由普通会话记录结果 |

补充规则：

- 对周期计划，暂停先提交，随后明确“运行一次”，该次运行有效，任务仍保持暂停；运行一次先提交、暂停后提交，暂停可以取消它尚未消费的输入。once 若运行一次先成功提交，配置已经自动移除，之后暂停返回不存在；取消其输入使用普通会话队列入口。并发顺序沿现有 session writer 事务决定。
- 尚未派发的过期 once 计划恢复后立即到期；已派发的 once 配置已移除，没有恢复或重新启用入口。需要再次安排未来执行时新建计划，遵守唯一 ACTIVE 限制；只需重试工作时在原会话明确提出。
- 运行一次的提交反馈复用全局 toast，不在任务页插入提示条，也不把提交成功表述为执行完成。任务按钮在排队或执行期间禁用，分别显示“已排队”或“运行中”，结束后恢复“运行一次”。
- 同任务的重复点击、多个窗口并发提交都复用已有 PENDING 或正在 RUNNING 的输入，不追加一轮；输入可以来自 TIMER 或 RUN_ONCE。若两者同时存在，优先确认正在运行的输入。继续保留原提示词、权限、模型和来源快照，不以新配置改写已接受输入。
- 正常完成、失败或停止后，新的运行一次请求可以再次提交；相同命令的重试始终确认原输入，即使它已经结束或取消，也不会重新运行。只针对手动提交防重复，自动到点的既有排队及 PENDING 合并规则不变。
- 后端在既有 session writer 事务中检查队列项及其消费轮次，并在最终准入再次检查，覆盖准备期间的竞态；不新增持久状态、锁 owner 或冷却时间。前端同步拦截重复点击，并刷新排队、运行状态；后端仍是准入权威。
- 自动到点只接受 ACTIVE 的有效 due；manual 不要求 ACTIVE。UI、HTTP 和模型工具使用同一 owner，不能只靠按钮禁用维护规则。

### 3.1 一次性计划自动移除

“仅一次”由保存的时间规则 `schedule.kind=once` 决定，不由按钮名称判断。once 经自动到点或用户点击运行一次 成功接受后，都消耗该唯一计划并移除配置；提前运行一次后不会在原预约时间再次触发。周期任务的“运行一次”只是额外提交一轮，不删除周期配置、不改变暂停状态。

移除时点是“输入成功进入普通会话队列”，不等待模型回复、工具成功或业务目标达成，也不由模型决定是否清理。接受/合并队列项、保存既有命令确认事实与删除 once 配置，在同一 session writer 事务提交；回滚时不留下半份接受或丢失计划。

- 自动移除只清理配置，**不能调用会取消 PENDING 的普通 delete 操作**。已接受输入、来源快照、命令确认与历史不依赖任务行继续存在；服务重启仍沿原 scheduled PENDING 恢复入口处理。
- 提交失败保留计划。timer 的明确准备失败沿既有规则暂停并展示原因；manual 返回动作错误并保持原配置。此时不宣称已执行或已移除。
- 模型/工具执行失败、被停止或输入后来被用户取消，都不恢复计划、不自动重投。失败与取消保留在普通会话；用户可以明确要求重试或新建预约。
- 回执丢失后，相同命令重试从既有 command/queue 确认，不依赖已删除任务行，也不再次入队。新的 UI 运行一次动作指向已移除 ID 时返回不存在，不能自动重建。
- 有同任务 PENDING 时合并仍保留该项的冻结值，然后移除 once 配置；不会因清理误取消旧项或升级其授权。
- 若任务在旧轮次运行期间被改成 once，运行一次只确认该旧轮次，不移除尚未提交的新 once 配置。
- 本次硬切删除计划级 COMPLETED 状态及其筛选、恢复/改期分支、界面“已派发”留存项；同步 clean-v0、API/工具、测试与文档。历史来源标识继续可读，不新增完成事件、清理任务或影子状态表。


### 3.2 聊天中立即执行

用户说“现在执行这个保存任务”时，模型按需用 list/get 读取指令，在当前轮使用普通工具完成工作。模型工具仅管理计划，不提供 run_now，也不会为这项请求再排一个后续 turn。当前轮执行本身不改变自动计划，不消耗 once 预约；只有用户同时要求修改、取消未来安排时，才执行对应计划管理操作。

这条真人聊天请求仍按普通真人输入处理；它与 UI 提交的 SCHEDULED_TASK 来源不同，适用原来的上下文和隐式召回规则。现有定时输入不触发隐式召回的合同保持不变。

## 4. 一个会话最多一个自动计划

限制精确定义为：同一会话同时只有 0 或 1 条 ACTIVE 配置。PAUSED 可以保留多条；显式单次请求不新占 ACTIVE 名额，once 成功入队后还会释放其原有名额。这不是会话任务数、历史条数、运行次数或寿命上限，也不是跨任务执行互斥锁。

- 同一工作的时间或提示词变化：优先编辑现有计划。
- 将自动工作从 A 换成 B：明确暂停 A、启用 B，保留 A 配置。
- 临时执行 B：允许运行一次，即使 A 仍 ACTIVE；A 的自动计划不改变，输入按普通队列排序。
- A、B 都需要长期自动执行：使用不同会话；不靠反复 run_now 模拟第二个自动计划。

创建的顶层可选字段 `status` 未填或为 `null` 时保存为 PAUSED；显式 PAUSED 同义，显式 ACTIVE 才启用。已有 ACTIVE 不妨碍新增 PAUSED；显式创建 ACTIVE 或恢复计划才检查冲突，不自动暂停另一个计划。非法状态返回请求错误。

当前管理页“新建任务”会创建新的快速开始会话并保存暂停计划，用户可通过列表开关启用。不要把上述限制误写成整个应用只能有一个计划。

## 5. 开关与原子切换

交互：任务页以 toggle switch 表示自动计划状态。关闭开关即暂停；打开 B 时，同会话没有 ACTIVE 则直接启用，有 ACTIVE A 则原子暂停 A 并启用 B。点击开关本身就是切换授权，不再弹确认或要求第二次点击。互斥只限同一会话，不影响其他会话的开关。模型收到“把 A 换成 B”也已有切换授权；仅收到“新增 B”时不能自行推断可以暂停 A。

实现由既有 scheduled repository 的 session writer 事务拥有：

1. 校验会话、权限、生命周期、A/B 身份及各自 expected_revision；确认 A 仍为预期 ACTIVE。
2. 按既有暂停规则暂停 A 并取消 A 的 PENDING；运行中的 A 不被停止。
3. 启用存在的 PAUSED B 并按其规则计算时间；新建 once B 必须提供合法的未来时间。创建新 B 的替换场景，同事务创建 ACTIVE 配置，不适用独立 create 的暂停默认值，target 不接受 status；已自动移除的旧 B 不能作为恢复目标。
4. 任一步失败整体回滚；成功提交后发既有 process-local wake。部分唯一索引继续兜底。

不以“先 pause HTTP，再 resume HTTP”宣称原子切换，也不增加恢复任务或补偿状态机。沿用 canonical 配置行、现有取消接缝、revision 与数据库事务，不新增表、事件种类、subject、append guard、durable job 或 fingerprint。

工具使用 `action=switch`，源计划由 `task_id/expected_revision` 标识；目标为 `{kind: existing, task_id, expected_revision}` 或 `{kind: create, values}`。HTTP 使用 `POST /api/scheduled-tasks/{task_id}/switch`，正文携带 `expected_revision/target`。UI 打开暂停计划的开关时查询同会话 ACTIVE，存在其他 ACTIVE 则直接调用 switch，否则调用 resume。查询与提交之间发生版本冲突时报告错误并刷新真实状态，不使用过期版本强制覆盖。产品切换只走此原子入口；单独暂停和恢复仍是独立操作。

## 6. 触发来源与授权

`ScheduledTriggerSource` 闭合为 `TIMER` 和 `RUN_ONCE`，只区分自动触发与运行一次。仅定时任务页 UI 通过 HTTP 调用 `ScheduledTaskService.run_now(request)`，由该 owner 固定产生 RUN_ONCE；timer 固定 TIMER。模型管理工具没有 run_now 动作，schema 和运行时校验均拒绝该动作。`ScheduledAdmission` 和 `ScheduledProvenance.trigger_source` 携带该值，queue 的 `scheduled_trigger_source` 受数据库约束。公开请求和 service 方法都不提供按发起人选择来源的参数。

| 来源 | 模型应如何理解 |
|---|---|
| 自动到点 | 按已有计划提交保存提示词；不是新的真人授权 |
| 运行一次（用户点击定时任务页） | 按保存的任务内容提交一次执行；周期计划保持原状态与时间，once 接受后自动移除；不改变既有权限和实质限制 |

来源由 runtime 的实际操作确定，不能从 task.prompt、按钮文案、时间是否落在周期网格上、当前 PAUSED 状态或工具参数中的自报身份推断。manual 仅是 RUN_ONCE 的内部派生判断，不代表真人身份。执行层不保留 USER/AGENT 单次来源分叉。用户在聊天中要求立即执行某个保存任务时，模型按需读取该任务指令并在当前轮完成；不创建额外 scheduled 输入。HTTP 与模型管理工具保留各自既有的请求校验和权限机制。

来源沿普通输入的冻结、queue 消费、USER entry、模型输入、历史、fork、压缩和 replay 保持；重试与合并不改变已接受来源。优先复用现有 command/input owner；需要新增来源值时，应仅承载这个独立的授权语义，不建额外事件账本、映射表或送达回执。

用户暂停自动触发与禁止具体业务行为不同。“停止每十分钟问好”不能被当作永久禁止用户再次运行一次；“不要发送邮件”仍约束之后的单次运行。运行一次只提交该份保存任务，不默认撤销其他有效禁止或更正。收到 UI 提交的任务或聊天中的立即执行请求时，不能仅因计划暂停而拒绝执行，也不能绕过实质禁止。实质限制冲突时，说明具体冲突并请求所缺信息，不把 PAUSED 当作理由。

模型使用冻结来源判断本次是自动触发还是运行一次，不能因为任务 PAUSED 就断言调度坏了或建议删除。当前 PENDING 为 NULL 也不能证明过去从未排队，可能已经消费。manual 命令确认摘要同时绑定可信来源；把同一已接受命令改称自动触发会冲突；UI 重试同一完整请求采用原命令的确认规则，合并到既有 PENDING 则继续保留原输入来源。

## 7. 提示词职责

提示词按职责分配必要规则，避免在多个位置反复说明同一生命周期：

- `src/pulsara_agent/ports/system_prompt.py`：未来安排与当前轮执行的选择；用户可从任务页运行暂停计划、周期运行一次保持原状态；once 接受后移除不等于执行成功、不否定已接受输入，无需清理或自动重建；已有权限与实质限制继续适用；有具体信息缺口时才检索。
- `src/pulsara_agent/capability/builtin_catalog.py`：计划管理的去重、完整更新与版本冲突；最多一个 ACTIVE；明确授权后的原子切换；日历和时间边界；编辑、暂停、删除、停止回复及恢复各自的影响。不讲 UI 的 NEW_TURN、时间游标或回执确认机制。
- `src/pulsara_agent/scheduling/requests.py`：字段填写与默认值、分页时保留筛选条件、权限不得升级或暗中降级绕过拒绝。保留每个 action 的 required/optional 字段签名；OpenAI adapter 会展开根 oneOf，签名仍用于说明各动作字段边界。未修改字段的保留规则统一放在工具描述，不在各字段重复。
- `src/pulsara_agent/model_input/lowering.py`：保留可信 provenance JSON、自动或任务页提交的来源说明，以及在有效权限和实质限制内执行的简短指令。压缩保留请求复用同一包装，不重复暂停、once 或计划管理说明。

已有目标与新建目标的 switch 参数由各自 schema 定义：源计划必须携带版本；已有目标携带自己的版本，新建目标携带 values。提示词不再笼统要求双方 revision。

核心指引：

> 仅一次计划在成功提交到会话队列后由 runtime 自动移除；这不代表工作已完成，也不会取消该次输入。无需再调用 delete 清理，不要因任务 get 返回不存在就拒绝执行已接受输入或自行重建计划。提交失败时保留配置并报告原因；执行失败在原会话处理。周期计划的运行一次保留原计划和状态。

SYSTEM 与 provider tools 的新措辞只在新 cold epoch 或明确采用的 compaction successor 构建时安装。现有 epoch 内保持已安装 SYSTEM/tools 字节相同、messages 仅追加；不得为了让当前会话立即理解新规则改写冻结前缀或历史来源。文档和代码改动不等于已有在线会话已经切换提示词。

## 8. 界面措辞

- “立即运行”改为“运行一次”；PAUSED 仍展示该操作。
- 点击时立即防重复；排队或运行中禁用，终结后恢复。提交、重复请求、失败及结果未知均使用全局 toast。结果未知时保留原请求和工具栏“确认上次提交”入口，即使 once 条目已消失也能确认；确认不生成新命令。
- 用开关替代状态徽章和暂停/恢复按钮，开关有包含任务名的无障碍名称与真实 checked 状态；不另加教学小字。
- 会话页中，用户从任务页提交与自动触发的输入，发送者名称统一显示“定时任务”；内部仍保留 RUN_ONCE / TIMER 来源。任务页操作按钮仍为“运行一次”。
- 打开 B 的开关授权同会话原子切换，不弹确认；等待提交期间禁用开关，成功后以服务端状态刷新，失败时报告错误并刷新，不显示虚假的已启用状态。

### 9.1 记忆与会话检索的现状和边界

当前定时输入（包括 UI 运行一次）是 SCHEDULED_TASK，`provider_dispatch._activation_subject_for_anchor` 将其归为 ROOT_NON_HUMAN_TRIGGER。新一轮自动记忆/历史召回只在 ROOT_HUMAN_PROMPT 分支准备。因此，定时提示词本身不会作为一条新真人消息触发隐式召回，也不会因此跑一遍 Embedding / Decision / 历史检索。

这不等于“定时任务完全没有记忆或不能检索”：

- 原会话上下文、摘要和已经安装的记忆/历史摘录仍然存在；不能为定时请求清空或重写前缀。响应偏好还有独立的刷新路径，它不等于一次新语义搜索。
- `memory_search`、会话搜索与展开工具没有因为 scheduled 来源而被统一禁用。模型在工具可见、授权与记忆使用策略允许时，仍可主动检索。
- 用户在运行途中发送真人 steer 是独立的新真人输入，可能按原规则触发召回；不能将其归因于定时器自动搜索。

本次不新增“定时任务禁用所有检索”的产品限制。模型指引为：先使用保存的任务指令和已有上下文，不因定时触发惯例性搜索记忆或会话；只有任务存在明确的信息缺口、需要既往记录时才使用可用检索工具。RUN_ONCE 仍保持 SCHEDULED_TASK / ROOT_NON_HUMAN_TRIGGER，不把保存提示词重新分类为 ROOT_HUMAN_PROMPT；两种来源均不打开隐式召回。用户若另外提出硬性禁用，必须另行定义工具与权限边界，不能靠文案保证。

真实 provider 验证只读使用有效 Pulsara home 的保存配置，在核实的本机临时数据库和临时工作区运行，保留实际输入、工具输出与回复，只移除真实凭据。生产会话和计划不作为可修改测试夹具。
