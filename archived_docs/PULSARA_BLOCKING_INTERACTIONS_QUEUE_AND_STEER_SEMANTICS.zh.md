# 阻塞交互期间的消息排队与 Steer 语义

日期：2026-10-20

状态：已冻结（产品语义与验收契约，2026-10-20）。主代理与同一位 GPT-6 Astra high 子代理已完成交叉讨论和修订后复核，无剩余冻结阻塞项。生产路径已按本契约实施，包含 `CANONICAL_PREFIX_CONFLICT` 修复；已完成 DeepSeek Chat Completions high 的 Plan 提问、方案审批与权限阻塞真实会话实测；能力配置实测按用户要求停止。主输入框入口已按用户修正为仅普通发送入队。

## 1. 统一规则

用户在会话被交互卡片阻塞时，仍然可以正常输入和发送消息：

- **普通发送**进入现有消息队列，不替用户回答、授权、提交配置或批准方案，也不自动关闭卡片。
- **显式 Steer**表示“先停止等我处理这些交互，按这条新指示继续”。Runtime 取消该目标轮次尚未决议的交互，将工具调用如实结算，再追加用户消息；模型先看到工具结果，再看到新指示。
- **已经开始执行的操作**按真实执行状态处理。Steer 不能把已经保存的配置、执行的命令或成功的授权改写成“被用户取消”。
- **方案审批**是单独的生命周期边界：提交方案的轮次已经结束。此时 Steer 表示修改方案，开启同一规划工作流的修订轮次，不重写旧工具结果，不隐式批准或退出规划。

主输入框只保留普通发送：阻塞或运行期间提交的消息先进入队列。用户需要 Steer 时，点击该队列项中的“发送”将其转为引导；输入框发送键旁不提供独立“引导”按钮，也不提供绕过入队的直接引导入口。Runtime 根据转换时的实际阻塞状态选择正确处理方式，不让用户选择内部取消策略，也不根据自然语言猜测用户是否已经授权。

本次入口修正不改变气泡与内嵌引导的现有显示，相关展示语义另行讨论。

这里的“被用户取消”只描述被取消的那次等待或尚未执行的调用，不表示取消整个任务、退出规划、撤销既有权限，或回滚已发生的效果。

## 2. 范围与当前事实

生产前端当前有四种会话内嵌交互：`tool-confirmation`、`capability-form`、`plan-question`、`plan-draft`。卡片加载中、加载失败、提交中均属于同一交互生命周期，不能因卡片尚未渲染成功而拒绝普通输入。

能力表单覆盖 MCP、插件、Skill、Hooks 配置与确认；OAuth 还需要区分打开浏览器前和授权进行中。点击提交后卡片可能已经关闭，但该操作仍未完成，因此本规格也覆盖提交与执行的交界。

以下内容不归会话 Steer 取消：

- 能力页、设置页等用户级页面中直接发起的配置编辑、登录及其他操作。
- 其他会话、独立子任务、既有后台进程中与本次目标轮次无关的工作。
- 单纯的内容预览、非阻塞通知、Hooks 的非交互式拒绝，以及上下文压缩等内部执行阶段；这些沿用各自的排队和安全点机制。

会话切换不改变 Steer 的目标。非会话页的读取、刷新与登录归属继续独立于 active 会话。

## 3. 阻塞状态处理矩阵

下表的“工具结果”指模型实际收到的结果。卡片的关闭和状态显示从真实 owner 结果派生，不由前端先行假定成功。

| 阻塞场景 | 普通发送 | 显式 Steer | 原工具或交互如何结算 | 后续运行与权限 |
| --- | --- | --- | --- | --- |
| 本地文件、命令等工具等待权限确认 | 消息排队，确认仍保留 | 撤销尚未被接受的这次确认，不执行该调用，追加 Steer | 原调用返回“被用户取消”，与用户主动点击“拒绝”保留原因区别 | 当前轮次继续，沿用原权限快照 |
| MCP 外部操作等待权限确认，包括 native 和 meta 调用 | 同上 | 取消确认并释放对应待用执行许可，不发送远端请求 | 结算实际等待的 MCP 调用；meta 路径沿用现有结果包装，不额外伪造内层调用 | 不授权同服务的其他操作，不改变工具目录和 provider tools |
| 添加 MCP、编辑 MCP、配置插件 MCP 连接，尚未提交 | 消息排队，表单和未提交内容保留 | 关闭该轮次的待提交表单，丢弃此次提交载体，不保存配置 | 能力管理调用返回“被用户取消” | 当前轮次继续；已有配置、凭据和连接不变 |
| Skill 安装、启停、移除确认 | 同上 | 取消尚未提交的确认 | 未发生安装、启停或移除，原调用返回“被用户取消” | 不改变 Skill 采纳边界，不改写当前前缀 |
| 插件安装、替换、启停、移除确认 | 同上 | 取消尚未提交的确认 | 未执行这次变更，原调用返回“被用户取消” | 已安装插件及其数据不因此被回滚或删除 |
| Hooks 信任、撤销信任、启停确认 | 同上 | 取消尚未提交的确认 | 不改变信任或启停状态，原调用返回“被用户取消” | Steer 本身不赋予信任或执行权限 |
| MCP 移除、退出登录等确认，尚未提交 | 同上 | 取消这次确认 | 不移除连接或清除凭据，原调用返回“被用户取消” | 当前轮次继续 |
| OAuth 登录卡片，尚未点击“前往登录” | 消息排队，卡片保留 | 关闭此次登录确认，不启动 OAuth | 原调用返回“被用户取消” | 不打开浏览器，不清除既有登录 |
| 已点击“前往登录”，浏览器登录或令牌交换尚未结束 | 消息排队；授权 owner 继续工作 | 取消该会话调用对登录完成的等待，追加 Steer；全局授权流程继续由授权 owner 持有 | 原调用只报告“等待登录被用户取消”，不得声称撤销授权或保证没有令牌落盘 | 不必等待用户在浏览器完成；后来的登录结果只更新原连接的用户级状态，不重新完成旧调用 |
| Plan 提问，包含选项题和允许自由输入的提问 | 消息排队，提问保留 | 关闭尚未回答的提问，原提问调用返回“被用户取消”，再追加 Steer | 不伪造选项或自由文本答案；保留“取消提问”和“已回答”的区别 | 仍在同一规划工作流、同一活动轮次，继续规划，只读约束不变 |
| 方案等待审批，包含已展开的“提出修改”输入区 | 消息排队，审批保留 | 关闭旧审批为“请求修改”，使用完整 Steer 内容开启一次修订轮次 | 原 `exit_plan` 的“已提交审批”结果保持原样；没有新的取消工具结果 | 同一工作流保持 ACTIVE，继续规划；不批准方案，不恢复执行权限 |
| 审批期间，将已排队的用户消息转为 Steer | 不转换则继续排队 | 原队列退出、审批转为请求修改、完整输入进入修订轮次，在同一 admission 事务中提交 | 不生成取消工具结果，不另外发送一份用户消息；失败时按第 4.4 节保留原输入 | 复用同一 Plan 修订路径，不采用原队列的权限或模型绑定来覆盖规划 admission |
| 卡片确认或表单提交已经被 owner 接受，操作尚在执行 | 消息排队 | 立即接纳 Steer；撤销其他尚未决议的同轮交互，对已开始工作发出其已有机制支持的取消请求 | 依据实际结果结算：未执行、已取消、成功、失败或结果未知；不能统一写成取消 | 原调用所需的效果结算完成后，再向模型追加 Steer；授权等待采用 OAuth 专门边界 |
| 确认、回答、审批已经结束，但前端还显示旧卡片 | 消息正常排队或在空闲时开始新轮次 | 读取实际 owner 状态，按仍存活的目标处理；不得撤销已完成的决定 | 已有结果不改写；旧卡片按状态刷新消失 | 目标轮次已经结束则明确返回目标失效，不悄悄转发到新轮次 |

尚未提交的能力表单只会被关闭，不会把模型预填值、API Key、用户未提交的编辑或浏览器凭据带进 Steer、工具结果或会话历史。普通发送不清空用户在卡片内写的内容。

## 4. 普通发送的队列契约

### 4.1 入队不等于决议

所有上述阻塞状态都允许用户主动发送的有效消息进入现有 FIFO。`PLAN_REVIEW_PENDING` 不再作为这类普通消息的入队拒绝原因；它仍可作为消费者“现在不能创建新轮次”的条件。

消息入队后：

1. 界面明确投影为排队消息，保留原内容与附件，不冒充已进入模型上下文。
2. 交互卡片继续存在。队列不自动回答 Plan 提问，不默认同意权限，不自动提交表单。
3. 活动轮次未结束、仍有审批待决，或当前执行 owner 尚未释放时，队列保持等待。
4. 阻塞解除且活动轮次结束后，按 FIFO 创建后续普通轮次。FIFO 约束普通队列内部；审批、修订等 Plan 控制产生的续接先获得执行 owner，不能被旧普通队列插入。不得绕过普通队首，也不把队列消息偷偷改成 Steer。
5. 支持将已排队的用户消息转为活动轮次 Steer，也支持在审批期间转为修订 Steer。显式选择的这条消息可以退出普通 FIFO，这不是消费者跳过队首；转换的唯一生效与失败规则见第 4.4 节。

### 4.2 权限在真正创建轮次时定案

入队冻结原始输入、显式目标、用户选择的 requested permission mode，以及现有模型配置绑定规则要求冻结的值。等待期间尚不存在的目标轮次，不应提前持有已经定案的执行权限快照。

消费用户普通消息并创建新轮次时，依据此刻已经提交的规划状态，计算并冻结唯一的 effective permission snapshot。例如，消息排队时在规划，之后用户批准方案，不应仅因规划版本变化就丢弃这条消息；取消方案后同理。

一次性的取消／退出 Plan handoff 也在真正创建轮次的同一 admission 事务中选择与领取，而非依赖入队时的旧观察。这样，先排队、后取消方案的消息仍能正确承接已提交的取消事实；不同消息不能重复领取同一 handoff。

这是本契约明确要求的**用户 NEW_TURN 队列与轮次 admission 边界 hard-cut**：旧的“入队时冻结未来轮次的 Plan overlay、之后因审批变化拒绝该消息”的规则需要同步替换，不能在旧路径外再加一套补丁。用户原先选择的 requested mode 不得被悄悄改成界面此刻的 mode。

现有活动轮次的权限快照不变；Steer 始终继承目标轮次。定时输入及其他非用户输入不因本规格自动改变 admission 契约。目标已删除、工作区不可用、模型绑定不可用等独立问题仍可得到明确失败，并保留可供用户处理的原消息。

### 4.3 UserPromptSubmit 仍是提交时观察

`UserPromptSubmit` 继续在普通用户消息入队前执行。它看到的是提交时依据 requested mode 与真实 Plan 状态投影出的 effective permission mode，不是 requested mode 的冒充值，也不是未来轮次的执行授权。

- Hook 执行到入队事务提交之间，仍须 exact-join 同一权限与规划观察。期间观察改变则明确拒绝本次提交，保留用户输入；不自动重跑可能有副作用的 Hook。
- 入队提交后，不再拿这个旧观察约束未来轮次的权限；审批、取消或退出规划不触发 Hook 重跑，也不因此拒绝已排队消息。
- 普通消费只在真正创建轮次时冻结执行权限。工具授权读取该轮次的 canonical permission snapshot，不读取 Hook 的历史字段。
- 同一提交的并发请求与 ACK 丢失继续复用现有命令查询和进程内 Hook attempt；不新增跨崩溃的 Hook 恰好一次执行保证。
- 队列转 Steer 不重跑 `UserPromptSubmit`。绑定原队列项的同步 NEW_TURN Hook context reservation 随原队列因果 owner 退休，不转投别的轮次；转换只转移完整用户输入。独立的异步 ROOT background context 仍沿用现有 scope 与 causal 规则，不因转换而清空、重标身份或增加交付保证。Hook 附加上下文本来是进程内建议，本规格不把它升级为持久交付保证。
- 主输入框提交先执行普通入队 Hook；随后从队列转为 Steer 不重跑 Hook。卡片修改意见继续走专门的 Plan admission，不因 typed `USER_MESSAGE` carrier 而额外执行一次普通入队 Hook，也不新增 Steer Hook 事件。

实施需替换“Hook 的提交时观察同时就是未来执行快照”的旧契约，保留准入时检查，删除入队成功后依赖旧 Plan overlay 的消费门禁。

### 4.4 排队消息转 Steer 的两种目标

请求必须携带原 queue item 身份以及用户发起转换时看到的显式目标：运行中为 session/turn，审批中为 session/workflow/interaction/revision。服务端不根据新 active 会话或新审批自动重定向。

| 转换目标 | 同一 admission 事务必须确定的事实 | 成功后 |
| --- | --- | --- |
| RUNNING 轮次 | 原 NEW_TURN 项仍 PENDING；目标仍可 Steer；原项退出；对应活动轮次 Steer 项接纳 | 原消息不再被普通消费；按第 5 节处理旧批次与输入追加 |
| OPEN 的 DRAFT_REVIEW | 原 NEW_TURN 项仍 PENDING；审批版本仍匹配；原项退出；审批变为 REVISION_REQUESTED；完整 typed 输入与唯一修订轮次发布 | 复用第 6.2 节修订 admission；不再创建第二份普通消息或另一份修订正文 |

转换读取原 canonical prompt owner 的完整内容与附件引用，不把界面文本摘要当原消息，不复制凭据或表单草稿。单个原队列项与单次审批各自只有一个赢家；同一转换 command 重复提交只确认原结果，携带不同目标或内容的重用必须拒绝。

消费、取消原队列项、另一转换或审批决议先提交时，本次转换明确失败：原项若仍待处理则保留，若已由赢家消费或取消则呈现赢家事实，不复活它。转换事务提交前的校验、准备或写入失败不移走原项，也不关闭审批。

转换已提交后才发生执行、provider 资源测量或目标终止失败，保留转换后的输入及明确失败状态，不恢复原 NEW_TURN 项，不自动重试或复制到新轮次。原输入不能在两个入口再次生效。

运行中转换沿用目标轮次权限；审批转换由既有 Plan 修订规则确定规划权限和模型绑定。原队列的 requested mode、模型绑定以及此刻 composer 的配置均不覆盖该目标；这是用户显式转换的含义。尚未转换的其他普通队列项仍保留各自 requested mode。

## 5. 活动轮次 Steer 的顺序与范围

### 5.1 接纳先于取消

Runtime 先检查控制权、会话身份、目标轮次、完整 PromptContent 和此时可判断的单次输入资源边界，再接纳 Steer。无效输入、过期目标或无权限请求不得先关闭卡片、后告诉用户发送失败。接纳表示现有 queue/command owner 已拥有完整输入，不承诺后续 provider 消费和资源测量必然成功；接纳后的失败按第 5.4 节处理。

活动轮次的 Steer 绑定显式 session 与 turn；审批时的 Steer 绑定显式 session、workflow、interaction 及 workflow revision。它们分别对应活动执行和已结束轮次留下的审批，不能让服务端只按“这个会话当前有什么”重新猜测目标。复用现有身份与版本，不新增 fingerprint 或目标注册表。

Steer 在现有命令与 prompt queue owner 中只有一个身份。接纳后即使请求连接断开，也不能变成“卡片已经消失，消息却没有 owner”。复用现有命令查询和结果未知处理，不新增消息回执表、恢复作业或通用执行日志。

### 5.2 取消目标轮次旧批次的未派发调用

交互层面的关闭只作用于这个目标轮次已经产生、尚未被接受的交互，包括当前可见卡片和已在等待队列中的同轮确认。不能只关闭第一张卡片，紧接着又用同批第二张卡片挡住已经接纳的 Steer。已接受决定与工具是否派发分别按下面的边界处理。

接纳 Steer 后，Host 与原执行 owner 协调派发边界，不再晋升同轮旧交互。这里的派发是执行 owner 已接受该次物理执行工作的边界，不等于用户已点允许、表单已提交或 MCP 待用许可已取得。

- Steer 先赢得派发边界：旧模型批次所有尚未派发的调用都以现有 `CANCELLED_BEFORE_DISPATCH` 语义结算，之后不恢复。包括可见卡片、dormant 确认、尚未产生卡片的调用、已获确认但未派发的调用，以及无需确认的同批调用。
- 派发先赢：保留已经接受的决定，按原 owner 支持的取消机制请求取消执行；以实际成功、失败、取消或未知结果结算。不能因 Steer 已接纳而声称它一定未执行。
- 每次调用只形成一份最终工具结果。已完成的结果不改写；没有派发的调用不为结算而启动；不能把旧调用延迟到 Steer 之后再执行。

禁止继续派发的范围是这次 Steer 所打断、已经由原模型请求产生的批次，不是之后新模型请求的调用，也不创建跨轮次禁用状态。多个 Steer 在同一个未结束的批次交接中共享已完成的取消事实，不重复生成结果。

该范围不扩大到其他会话、独立子任务或全部 MCP 连接。下一次模型调用依据新指示提出的新交互，仍可以正常显示；不增加跨轮次的“禁止再询问”状态。

### 5.3 模型观察顺序

在现有安全点上形成下列可见顺序：

1. 原模型请求已经包含的工具调用。
2. 这些调用的真实结算结果；未获决议的交互调用得到“被用户取消”。
3. 按接纳顺序追加的完整用户 Steer 内容。
4. 下一次模型调用。

结果和消息可以由现有不同 owner 写入，不要求为它们新增一个持久化“大事务”。但在需要的结算完成之前，Host 不得启动下一次 provider 调用。某步失败时，保留已经接受的消息及已经提交的事实，按第 5.4 节明确结算失败；不能重复执行工具来凑齐顺序。

正常完成取消交互与追加 Steer 不终止整个轮次；显式停止与失败按第 5.4 节处理。任何路径都不改写已安装 SYSTEM/tools，不重新组装既有 messages 前缀。模型自行理解新的自然语言指示，Runtime 只负责取消、排序、权限和事实边界。

### 5.4 接纳后的资源失败与显式终止

工具取消结果会改变 canonical cut。下一次模型调用必须基于真实已提交的结果与有序 Steer 后缀重新准备、测量，并与发布后的 exact read 核对；废弃旧 prospective candidate，不放宽一致性检查，不重建已安装前缀。

- 后续 provider 输入资源不足：复用现有资源拒绝和轮次中断路径，未消费的 Steer 明确进入失败终态，原输入仍可读取。已提交取消事实不回滚，不复活卡片，不自动恢复原普通队列项或换目标重发。
- 结果写入或执行结算失败：不启动下一次 provider 请求。可由现有 owner 只读确认的提交先确认；已知失败或无法继续的目标按现有中断、队列失败规则结束。实际提交未知则使用现有结果未知查询规则，不把已接受输入冒充尚未发送，也不新增自动恢复作业。
- 用户 Stop、ForceExitPlan、会话关闭或 Host 接管使目标终止：尚未 canonical 消费的 Steer 随目标终止明确失败，已消费的输入保留历史；均不自动续跑。Steer 接纳不凌驾于之后的显式停止。
- 普通 final 与 Steer 接纳竞争：正常 final 先提交则旧目标拒绝；Steer 先接纳则原轮次不能通过正常 final 把它遗留。这与显式停止、资源失败、中断的例外不同。
- 压缩或其他安全点交接：未接纳请求可按既有 busy／stale 规则明确失败并保留输入；已接纳输入仍由原 queue owner 持有，待 owner 交接后按实际 cut 准备。若目标已终止则明确失败，不长期悬置。仅显式采纳的压缩 successor 可以按既有契约改变 epoch 边界。

“保留输入”不承诺故障后继续执行。确认的失败必须有现有命令／队列终态及用户可处理的原内容；待处理只用于仍有存活 owner 执行或现有提交结果尚未确认的阶段，不能成为没有 owner 的无限等待状态。

## 6. Plan 两种阻塞的明确区别

### 6.1 Plan 提问

提问的原轮次仍 RUNNING。Steer 取消的是“等用户回答”这件事，不是取消规划。即使题目不允许自由文本，也允许用户先正常发送消息入队，再点击队列中的“发送”转为 Steer：它是一条新的用户指示，不是绕过题目规则提交一个 FREE_TEXT 答案。

QUESTION 需要表达“被 Steer 取消且已有取消工具结果”的闭合状态。复用现有交互终态 `CANCELLED` 与既有工具结果关联字段，并修改 clean-v0 的 QUESTION 约束；不能冒充 `ANSWERED`，也不能沿用“轮次中断、无工具结果”的 `ABORTED` 语义。工作流仍 ACTIVE，轮次仍受规划只读权限约束。

### 6.2 方案审批

原 `exit_plan` 已完成，方案审阅没有等待中的工具 future。因此不能把原结果改成“被用户取消”，也不能把 Steer 追加到已经结束的原轮次。

冻结规则：**卡片“提交修改意见”和审批期间排队消息转 Steer 使用同一条修订 admission 路径。主输入框发送始终先入队，不直接触发修订。**

- 原审批从 OPEN 转为 REVISION_REQUESTED，工作流继续 ACTIVE，版本按既有规则推进。
- 新建一个修订轮次。真正的用户输入保留为 typed `USER_MESSAGE`，关联 `REVISION_REQUESTED` handoff；不把输入伪装成系统生成的 Plan 控制正文。
- 卡片的文本修改意见也转为同一 canonical PromptContent。队列转换的文本、图片及其他现有支持的输入完整保留，不能仅提取文本塞进旧 `feedback: string` 字段。
- 用户输入在模型上下文中只出现一次。Plan handoff 只表达修订事实，不再复制一份反馈正文。
- 继续使用规划权限，不自动批准、执行或退出规划。用户要批准或退出，仍走明确的现有控制。
- 修订必须含现有 PromptContent 校验认可的真实有效内容，文本或支持的附件均可，不能误拒只有图片的输入。空内容在 transition 前拒绝，原审批保持 OPEN；删除旧的无内容 `feedback=None` REVISE 分支，不制造假的人类消息。
- 修订轮次的权限与模型绑定由既有 Plan continuation admission 确定，不走普通 NEW_TURN 消费，不采纳 composer 或转换来源的 requested mode 来升级规划权限。
- Plan transition、typed 输入和唯一修订轮次在同一现有 admission 事务中发布；排队转换还包括原队列项退出。失败不留下已经关闭审批却没有新输入 owner 的状态。事务后的执行失败保留真实 transition，不重新创建续接。

这是对旧 REVISE carrier 与协议输入边界的明确 hard-cut 要求；实施时同步替换卡片修改意见与队列转换路径、carrier 约束和 reader，不保留两套修订正文，也不以通用 Steer 名义重开冷 epoch。

如果审批决议已经被接受，新请求不能覆盖它。对原审批的 Steer 返回明确的目标失效，保留输入；用户可以随后针对新的执行轮次发起 Steer。不得仅因新旧轮次属于同一会话，就自动把消息送进已经获批的执行轮次。

多条 Steer 按接纳顺序追加，仅适用于仍绑定同一 RUNNING turn 的请求。审批首条 Steer 关闭旧 interaction 后，后到且仍指向该 interaction/revision 的请求必须失败并保留输入；不自动合并进修订轮次。同一 command 的重试先确认原赢家，不应因审批已经关闭而误报该重试失效。

## 7. OAuth 和已经发生的效果

OAuth SDK 与授权 owner 继续拥有协议、回调、令牌交换及凭据存储；会话 Host 只拥有这次工具调用是否继续等待。当前 `begin()` 可以复用同一连接已有的登录流程，所以不能用“取消一个会话等待”推导“取消全局登录”。

统一采用：浏览器登录开始后，Steer 解除会话等待，授权流程仍由用户级 owner 持有。用户若要停止登录，使用该连接已有的取消登录操作；Steer 不隐式注销、不清除令牌、不关闭其他调用共享的授权流程。

适配层用 asyncio 已有的 task/shield 机制隔离“取消等待”和“取消授权 task”，复用现有登录 owner 与 SDK 生命周期，不复制 OAuth 状态机，也不增加持久订阅者或授权恢复任务。

取消等待后的迟到完成：

- 仅在原配置、flow 与凭据 owner 仍有效、且原 owner 接受该结果时更新用户级登录状态；不得绑到此刻 active 会话。注销、删除／更改配置、替换插件实例或重新登录使旧流程失效时，迟到结果不能恢复它们。
- 不向已取消调用补写第二份工具结果，不复活旧卡片，不自动恢复旧模型任务。
- 不因已取消会话调用的完成通知抢焦点；其他独立、仍有效的用户登录操作保留自己的通知行为。
- 若成功已经先被原工具接受为结果，保留成功结果，再追加 Steer。

文件写入、插件安装、命令执行和外部 MCP 副作用仍由原执行 owner 负责。能安全取消则请求取消；无法取消则等待现有结算边界。超时或远端结果未知如实呈现，不说“未执行”，也不为 Steer 自动重放请求。OAuth 解除等待是上面明确的 owner 边界，不是允许任意写操作在后台失去结算归属。

## 8. 竞态与失败矩阵

| 竞态或失败 | 冻结规则 |
| --- | --- |
| Steer 与卡片“允许／提交／回答”同时到达 | 同一交互的 owner 决定唯一赢家。Steer 先赢则旧卡片提交失效；决议先赢则保留决定及真实效果，Steer 随后按目标实际状态处理 |
| Steer 与已获确认调用的派发同时到达 | 以执行 owner 的实际派发边界为准：Steer 先赢则执行前取消，之后不恢复；派发先赢则结算真实效果，不能把“已允许”或“已取得许可”当成已经执行 |
| Steer 与方案批准、修改或取消同时到达 | 用现有 workflow revision、interaction identity 与决议事务竞争；只允许一个 transition。失败方不能再创建第二个续接轮次 |
| Steer 输入校验或接纳前资源检查失败 | 不取消交互，不清空草稿；排队转换事务未提交时不移走原项，不改变审批 |
| 同一 Steer 重复发送或 ACK 丢失 | 查询或重用同一 command identity；正文、取消结果、Plan transition 和修订轮次各自最多生效一次 |
| 多条 Steer 连续到达同一 RUNNING turn | 依接纳顺序处理，不用“最新一条”覆盖前面的消息。下一次模型调用前已经接纳的消息，在现有单次资源边界内按顺序追加；共享已有取消结算，不重复结果 |
| 多条 Steer 指向同一审批，或旧审批请求迟到 | 第一条有效 transition 成功后，其他 command 的旧目标失效，保留各自输入／原队列赢家状态；不自动投给修订轮次。同一 command 重试确认原结果 |
| 普通 final 与 Steer 接纳同时到达 | Host 与 canonical 提交决定唯一顺序：Steer 先接纳则正常 final 必须让其进入后续消费；final 先提交则旧目标明确失败，不静默重定向 |
| Stop、ForceExitPlan 与 Steer 同时到达 | 终止先提交则不接纳旧目标；Steer 先接纳也不能阻止之后的显式终止。未消费输入明确失败，已消费输入保留历史；规划状态按真实退出决定，不恢复旧卡片 |
| 会话关闭、归档／删除操作或 Host writer 接管 | 按现有会话生命周期 owner 的接纳／终止边界处理；目标不再可执行时未消费 Steer 明确失败，已消费输入不重放。显式删除仍服从用户要求的数据删除语义，不承诺被删除数据可供重发 |
| 排队转换与普通消费、取消原项、另一转换竞争 | 同一源项只能被一个 admission 消费／取消／转换；失败方读取赢家事实，不恢复已消费项，不制造第二份输入 |
| 审批转换与审批决议、消费槽位交接竞争 | 源队列退出与修订 transition、输入、轮次同事务；审批赢家唯一；Plan 续接先占执行 owner，普通消费者不能插入 |
| 入队 Hook 与规划状态变化竞争 | Hook 到入队提交仍 exact-join，变化时明确拒绝并保留输入，不自动重跑 Hook；已入队后变化不再用旧观察拒绝该消息 |
| 转换后资源不足、执行失败或目标终止 | 保留转换后的输入与明确失败，不恢复旧 NEW_TURN 项，不自动转发；审批 transition 已提交则不撤回或重复创建修订轮次 |
| 取消结果写入与后续 provider 测量竞争 | 结果提交后按真实 cut 重新准备；资源失败按现有拒绝／中断路径终结输入，已提交取消不回滚；结果未确认不得继续 provider 调用 |
| 压缩、安全点或执行 owner 交接 | 接纳前 busy／stale 明确返回；已接纳后由原输入 owner 持有，按交接后的有效 cut 处理或随目标终止失败，不绕过 guard，不引入新 epoch 边界 |
| 请求连接断开或 controller detach | 不回滚已提交的决定或输入。按原交互生命周期关闭 process-local 等待，现有持久 Plan 状态按其 owner 规则保留；不新增崩溃续跑保证 |
| 进程退出发生在取消与追加之间 | 已提交输入仍属于现有 queue/command owner，执行状态按现有中断规则处理。重启不复活旧 future，不为证明整组取消成功新增恢复账本 |
| 卡片过期、被另一控制端处理或内容加载失败 | 以实际 owner 状态为准；错误必须关联原命令，连接保持可用，不落成无法解释的“发送状态待确认” |
| 同会话有旧队列消息 | 不因 Steer 删除普通队列，也不让旧队列插进原轮次的工具结算与 Steer 之间；原轮次结束后再消费 |
| 多会话共享 OAuth，某一会话 Steer 与授权完成竞争 | 只解除这次会话等待。结果接受先赢则保留成功；解除等待先赢则原调用只结算等待取消，不补写成功；共享 flow 仍由用户级 owner 持有 |
| OAuth 完成与注销、配置删除／更改、插件替换或重新登录竞争 | 复用授权 lane、当前配置／flow 与凭据写入守卫；只接受仍有效的原 owner 结果。旧回调不恢复已注销或删除的登录，不误取消新登录 |
| 外部副作用已发生但返回丢失 | 保留真实的结果未知状态；不靠重试推断未执行，不把 Steer 变成副作用重放入口 |

Steer 不自动退化成普通发送。目标失效时明确拒绝并保留输入，比悄悄改变目标、权限与执行顺序更可预期。

## 9. 已定位的前缀冲突必须独立修复

当前 reader 的 `_canonical_input_origin()` 用 `source_plan_workflow_id != None` 推断 `PLAN_CONTINUATION`。取消规划后的第一条普通消息也合法携带该字段，因此被错误分类，跳过 typed prompt hydration，将存储 JSON 当成正文。

已经通过真实 PostgreSQL、生产 gateway、Host、reader 与测试模型复现：准备时是 HUMAN_MESSAGE 和用户文本，写入后重读成为 PLAN_CONTINUATION 和存储 JSON，随后触发 `CANONICAL_PREFIX_CONFLICT`。生产 reader 现已按 entry kind 识别输入来源；同一用例与审批修改、纯图片输入均纳入真实 Host／PostgreSQL 回归。

正确边界必须是：**输入的真实来源与附带的 Plan handoff 是两个独立维度。** 普通用户消息、Steer 和修订意见都按自己的 typed carrier 读取，不能因为关联工作流就改成系统控制输入。取消规划、强制退出规划及本契约的修订用户消息均需覆盖。

新的 Steer 语义可以改变交互流程，但不能替代这个修复。继续保留发布前后 canonical exact comparison、已有 epoch 连续性检查及 append-only 约束。

## 10. 实施边界与验收

复用现有 Host、interaction coordinator、Plan repository、prompt queue、canonical prompt owner、工具结算和 MCP OAuth SDK。前端负责提交明确意图和投影真实状态；模型不决定哪个交互被取消，前端不先关闭卡片再拼接消息。完整 PromptContent 的传输需要最小协议调整，不能用新增 placeholder 或模型建议接口代替。

不增加持久事件种类、subject slot、append guard、产品关系或后台 job。QUESTION 取消结果与 Plan 修订仍由现有交互、工具结果、transcript 和 queue 行承载；实施若发现必须扩大这些类别，应先修订本规格说明独立必要性，不能自行追加。也不增加总轮次、总时间或总工具调用上限。

实施必须作为一次完整 hard-cut 删除本规格替代的旧门禁与 carrier 路径，更新 clean-v0、协议、生产代码和相关测试。验收证据以生产入口回归与代码交叉复查为准。

最低验收矩阵：

| 验收面 | 必须证明的链路与断言 |
| --- | --- |
| 四种卡片的普通发送 | 真实前端输入 → gateway → Host → PostgreSQL 入队；原卡片仍待决；解除阻塞后按 FIFO 执行；审批版本变化不吞消息 |
| 入队 Hook 与消费权限 | Hook 看到提交时真实 effective mode；提交前 Plan 变化明确拒绝，入队后变化不重跑 Hook、不丢消息；工具权限只取实际轮次快照；转换仅退休绑定原队列项的同步 Hook context，不将其误投当前轮次；独立异步 ROOT background 不被清空或重标 |
| 工具确认与能力表单 Steer | 真实卡片触发 → Steer → 原调用取消结算 → 用户消息追加 → 下一次模型请求；确认未执行、未保存配置且顺序正确 |
| native 与 meta MCP | 各跑一条真实 SDK 本地服务链路；取消确认后服务未收到调用，结果归属和包装正确，provider tools 保持不变 |
| 并行工具与多个待决确认 | 可见和 dormant 交互均关闭；含无需确认、已确认但未派发的调用均永久取消且不启动；派发边界双方各先赢一次；已执行的兄弟调用保留真实结果；新消息不被第二张旧卡片继续挡住 |
| Plan 提问 Steer | 不允许自由文本的题也可 Steer；不伪造答案；取消工具结果在新指示之前；工作流和规划权限保持 |
| 方案审批 Steer | 旧结果不变；一次修订 transition、一次新轮次；卡片修改意见与队列转换共用修订路径；主输入框只入队；纯图片有效，空输入拒绝且保留 OPEN；多请求旧目标不重定向；文本与图片不丢失、不重复，保持规划权限和修订模型绑定 |
| 排队消息转 Steer | 活动轮次与审批阶段各走真实前端／协议／数据库链路；与消费、取消、其他转换及审批决议双方各先赢一次；提交前失败保留原项，提交后失败不恢复原项；相同 command 重试只确认原赢家 |
| 取消与强制退出后的消息 | queued 与直接创建轮次、后续历史重读均保留真实 input origin；准备值与实际读完全一致，无 canonical prefix 冲突 |
| OAuth | 真实 SDK 回调与令牌存储链路覆盖成功、失败、共享等待与 Steer；会话取消等待不终止共享登录、不删除凭据；与注销、删除／修改配置、插件替换、重新登录竞争时旧回调失效，不复活任务或已删除连接 |
| 已提交效果与决议竞态 | 双方各先赢一次；真实文件／配置／命令结果不被取消文案覆盖；不重放外部效果；审批只创建一个续接 |
| 接纳、断线和重复提交 | 无效 Steer 不关卡片；接纳后断线能查询原输入；重复 command 不重复执行；旧目标明确失败，前端保留输入 |
| 显式终止与生命周期 | Stop、ForceExitPlan、关闭、归档／删除、Host 接管均覆盖提交先后与输入是否已消费；不吞消息、不自动转新轮次、不违背显式删除；正常 final 不能遗留已接纳的 Steer |
| 结果结算与资源边界 | 取消结果改变 cut 后重新测量；接纳后资源失败明确终结、输入仍可读取；结果写入失败不继续模型；不恢复卡片、原队列或旧 prospective candidate；安全点交接不绕过一致性检查 |
| 前缀与权限 | 同 epoch SYSTEM/tools 字节不变、messages 仅追加；活动轮次权限不变；Plan 修订不成为批准或权限升级入口 |
| 用户级隔离 | 切换会话或进入能力页不改变操作目标与 OAuth 归属；其他会话及用户级编辑不被当前 Steer 取消 |

测试应走生产入口和真实存储、SDK 边界，模型可使用可控测试替身以精确验证调用顺序。远端 OAuth、真实命令及不可撤销服务操作的人工验收独立记录，不以 mock 代替外部服务已验证的结论。

## 无方案退出规划（2026-10-20 补充）

用户确认新增 `exit_plan` 的无方案分支。`plan` 省略、`null`、空字符串或纯空白字符串时，不创建 `DRAFT_REVIEW`，不显示审批卡片；非空方案仍按既有规则提交审批。其他类型、未知参数和超出既有资源边界的输入仍明确拒绝，不能用无方案分支绕过校验。`exit_plan` 的唯一当前工具合同为 v2，不保留 v1 调用或双解码兼容路径。

模型显式调用工具才退出规划；Steer 自身不退出、不批准、不变更权限。工作流以 `EXITED` 结束，不伪造批准、用户取消或强制停止。工具结果以 `EXITED_PLAN` 确认退出，并按用户最新要求携带工作流保存的 `resume_permission_mode`。新的 `EXITED_PLAN` handoff 由已有 `PLAN_CONTINUATION` carrier 表达，不制造用户消息或气泡。它说明退出状态及恢复权限，指示继续原任务；不得重新实现未批准草案来冒充审批。

退出在既有 Plan 自动续接 admission 中完成：工作流终止、整批工具结算、旧只读回合完成、唯一的新回合及其 provider input admission 在同一事务提交。新回合恢复进入工作流时保存的权限，而非旧规划回合的实际只读权限、当前 composer 权限、最近普通输入或 Steer 来源队列的权限。新快照 overlay 为 NONE，继承来源指向旧回合；旧回合快照保持不变。恢复前本就是只读的，退出后仍只读。

无方案退出沿用既有批次屏障，同响应其他调用返回 `CANCELLED_BEFORE_DISPATCH`；模型在新回合重新调用需要的工具。自动续接优先于普通队列，后续 FIFO 消费不重复领取退出 handoff。沿用同 epoch SYSTEM/tools 不变和 messages 仅追加规则，不新增前缀重建边界。

复用现有 Host continuation owner、关系行、工具结果、事务、`PlanWorkflowExited` 和 `PlanContinuationAccepted` 事件。只扩展工作流状态和 handoff 值，不增加事件种类、subject、guard、产品关系、job 或持久恢复机制。提交前的 Steer／Stop／ForceExit、资源 admission 失败、提交后 ACK 丢失和关闭仍沿用既有唯一赢家与续接终止规则：失败不能留下已退出却未创建续接的半完成状态；提交成功后不重复退出或重复执行。

回归覆盖省略／null／空串／Unicode 空白、四种恢复权限、用户和模型两种进入方式、工作流保存权限与当前规划输入 requested mode 不同、真实文件写入／只读拒绝／询问授权、无审批交互、同批取消、FIFO 与前缀连续性，以及 admission 失败、ACK 丢失与取消竞态。此次不做真实模型实测。
