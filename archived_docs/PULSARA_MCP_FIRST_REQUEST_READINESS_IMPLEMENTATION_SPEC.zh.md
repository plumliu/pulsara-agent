# Pulsara MCP 首次请求就绪与 required 删除实施规格

状态：已实施，本机验收完成。日期：2026-11-03。

## 1. 产品合同

用户启用 MCP 后，Pulsara 在后台启动连接与目录发现。会话页面立即可用；首次模型请求冻结原生工具列表前，等待当前已启用 MCP 的首次连接与目录发现结束。成功的能力参与工具选择，失败的服务明确显示失败，模型使用其余能力继续执行。

完整删除 MCP **服务级** `required` 字段和“将此服务标记为必需”入口，不保留必需/可选两套启动行为。MCP Prompt 参数、插件连接输入及 JSON Schema 中表示参数必填的 `required` 保持原义，不属于删除范围。

本规格取代历史 MCP 启动规格中的 required/optional 分流及 required-first 排队语义。其余现行 MCP 权限、资源保护、执行所有权、调用失败续行和 provider 前缀连续性合同继续有效；历史记录不作为实现依据。

## 2. 用户体验

- 打开、恢复会话不等待 MCP 网络连接；历史、输入框和其他页面可正常使用。
- 用户发送后，若首次准备仍有 MCP 未结束，在现有执行状态区域显示“正在连接 MCP”，列出等待中的服务及“连接中／读取目录”。使用现有状态展示风格，不增加聊天消息、工具调用卡片或灰色说明文字。
- 失败的服务在现有 MCP 状态入口显示失败原因，例如连接超时、认证失败或目录发现失败；首次执行状态可显示“Firecrawl 连接失败，继续处理”。该提示不要求用户点击确认，也不阻止已就绪能力继续工作。
- 等待时仍可停止当前任务、关闭会话；停止后不发送模型请求。仍有排队输入时遵循现有队列和 steer 语义。
- 删除服务级 required 开关、详情字段及解释文字，不以另一个用户开关替代。

## 3. 等待的时间与范围

### 3.1 放在首次冻结之前

等待属于首次实际执行的 provider 输入准备，不属于会话创建，也不属于 provider 网络调用：

```text
打开会话 → 后台启动 MCP → 会话可操作
用户发送 → 采纳当前配置 → 等待首次连接及目录发现
         → 安装可用候选 → 冻结 SYSTEM/tools → 编译并发送首次请求
```

进入等待前不得持有 provider 输入快照、工具 surface borrow 或阻止停止、配置修改和连接候选发布的锁。结束后重新使用现有 safe point 采集当前事实，再冻结输入；不得沿用等待前取得的过期候选。

触发条件是当前执行即将建立一个没有已冻结根的 cold epoch，不能用 `model_call_index == 1` 或“新 turn”代替。已有 epoch 中的下一轮、工具结果后的续行、provider 重试和普通 MCP 重连均不重新执行此等待。

恢复会话后若生产链路建立新的 cold epoch，执行相同等待。子代理如独立建立 cold epoch，也通过同一准备边界，按其现有能力作用域选择工具；若使用已经冻结的继承根，则不得等待后改写继承根。不能为此扩大子代理 MCP 权限。

新用户输入、恢复会话已有的 pending 输入、定时输入和子代理工作均经过相同的实际执行准备边界，不得依靠桌面发送按钮或新 turn 分支提供等待。Host 构造只组装依赖；Core 完成会话注册后才启用队列消费。注册不等待 MCP 网络就绪，队列执行到 cold-epoch 准备边界时才等待首次 attempt。构造／注册与执行激活的职责见 [内核生命周期与服务组装规格](PULSARA_KERNEL_LIFECYCLE_AND_SERVICE_COMPOSITION_IMPLEMENTATION_SPEC.zh.md)。

实际执行使用的 headroom／预算前置准备同样受此边界约束：不得先取得 provider 输入快照，再在后续编译函数中补等 MCP。只读预算试算仍遵循下文的预览例外。等待结束后再取得本次准备的短期快照和编译期限；不能把正常连接等待误报为快照或编译超时，也不能借此延长既有物理操作超时。

显式采纳的 compaction successor 继续使用其现有冻结候选和采纳合同，本改动不额外等待网络，也不重选其已冻结工具。能力变化不得制造新的 epoch 或 compaction。

上下文占用预览、工具预算试算、会话列表和能力检查不能触发或消费首次等待，也不能安装 provider 前缀；辅助标题和建议请求不使用此 MCP 原生工具列表，不额外等待 MCP。

### 3.2 等待哪些工作

等待开始时捕获当前配置下**实际启用且已获准启动**的服务及其现有连接 attempt。禁用、未批准的 workspace MCP、缺失授权而不能启动的服务不发起网络操作；现有状态必须明确可见。

“结束”指该次 attempt 完成以下任一结果：

| 结果 | 首次请求行为 |
|---|---|
| 初始化、声明能力的目录读取、Pulsara 校验及候选发布完成 | 在 safe point 纳入可用候选，按现有策略选择原生或 META 路由 |
| 连接、认证、发现、校验失败，或既有 attempt 超时 | 显示具体失败，继续其余能力 |
| 当前配置被禁用、删除或替换 | 不再等旧 attempt；不采用旧配置候选 |
| 用户停止、Host 关闭、所有权失效 | 结束当前执行，不发送请求 |

仅 TCP/HTTP 已连接或 MCP initialize 已完成不算 READY，必须完成声明能力对应的目录发现与校验。SDK 负责协议、传输和通知，Pulsara supervisor 继续负责候选、资源限制和生命周期；不复制 SDK 协议逻辑。

首次等待观察既有 attempt 的完成结果，不能只轮询服务器当前状态：失败后自动重试可能立即使状态回到 CONNECTING，仍应允许首次请求继续。失败后的重试不加入此次等待。

等待期间新启用或替换的配置继续由现有配置 owner 启动；它们不扩大已经捕获的等待集合。最终 safe point 可以纳入此时已就绪且属于当前配置的能力，未就绪者按后到能力处理。这样无需反复重启等待，也不延长为“直到配置永不变化”。

已成功的 attempt 不要求重新连接。已有同语义可用候选的后台重连不让首轮等待物理替换完成；执行可用性仍遵循原有连接围栏，不能用保留的目录证明远端可调用。

## 4. 超时、调度与取消

- 复用 supervisor 现有单次连接与发现超时（当前默认 120 秒），覆盖 initialize 与目录发现；排队使用已有 discovery reservation，不把队列等待误判为远端超时。
- 不新增整会话超时、总重试次数或首轮统一总等待时限。多个服务在现有物理并发限制下排队，显示实际进度。
- 删除仅服务于 required 的启动等待超时和优先调度；服务按既有稳定配置顺序进入现有调度器，不新建调度系统。
- 首次 attempt 失败即可释放请求等待；自动重连继续使用现有退避和生命周期，不等待它最终成功。
- 等待当前执行可取消；取消一个等待者不取消仍由会话 supervisor 所有的连接任务。关闭会话才由现有 owner 取消并 join 物理连接和清理。
- 不持有 session 锁跨网络等待。取消、canonical/数据库故障、配置 owner 错误及物理清理失败不得被笼统归入“MCP 失败后继续”。配置变更的旧候选不得回写新配置。

## 5. 前缀不变性

同一 epoch 内，SYSTEM 和原生 `tools` 必须逐字节一致，messages 只能尾部追加。

- 首轮 READY 的 MCP 工具参与现有 native/META 选择；READY 不保证所有工具都会放入原生数组，仍遵循既有暴露策略、预算和 schema 兼容性限制。
- 首轮未纳入 native 的工具随后 READY，只能通过既有目录观察、`query_capabilities` 和 META 调用路径提供；不能插入已有原生数组，不能重发首轮或重建前缀。
- MCP 连接恢复、目录变化、管理工具操作和 UI 刷新不构成前缀重建边界。
- 工具结果后的下一次模型请求是正常 agent loop，继续复用相同原生数组；MCP 等待本身不产生试探性模型请求。

用户和模型看到的失败信息复用现有 MCP 目录和状态投影。模型侧运行时观察只在允许的消息尾部追加，不改写旧观察或 SYSTEM。

## 6. 实现落点与删除清单

| 位置 | 改动 |
|---|---|
| `mcp_config.py` | 从声明、运行配置、构建参数、校验、序列化和配置身份输入中删除服务级 required |
| `plugins/mcp_adapter.py`、MCP 管理 owner | 删除固定 required 值、编辑数据及配置导入导出中的字段 |
| `mcp/supervisor.py` | start 只启动后台工作；移除 required-first 和 required 启动等待；基于现有 attempt/task 提供首次准备等待及当前进度 |
| `host.py`、`provider_dispatch.py`、必要的 runner 接缝 | 在实际 cold-epoch 根冻结前接入等待，复用 safe point、连续性 owner 和取消机制；预览与已冻结输入路径不进入 |
| `mcp/contracts.py`、能力查询和桌面投影 | 删除服务 DTO、详情、模型可见投影中的 required；保留连接状态及诊断 |
| `frontend/components/mcp-editor.tsx`、前端类型与适配器 | 删除开关、数据字段及保存路径；等待和失败使用现有执行状态、MCP 状态展示路径 |
| CLI、bundled installer Skill、样例、文档及测试夹具 | 不再生成或宣传服务级 required，描述统一首次准备行为 |

这是完整 hard cut：不保留别名、旧字段读取、默认 false 占位、隐藏配置入口、双套等待逻辑或兼容分支。包含旧服务级字段的配置按未知字段明确报错；实施安装前需显式清理本机已配置条目中的该字段，保留其他配置和凭据。不得以运行时悄悄忽略旧字段替代清理。普通 JSON Schema 必填声明不能误删。

没有新增数据库表、迁移链、持久事件、任务、收据、完成标记或恢复机制。首次就绪与等待进度是可丢弃的进程内观察，直接归既有 supervisor 和执行准备 owner 所有。优先复用连接 task/outcome 和已存在的 attempt/config 身份，不另建结果注册表或分配新 ID；若实际实施发现必须新增对象身份，须使用共享 Pulsara ID 层。

## 7. 验证与验收

先迁移旧测试：仅冻结 required/optional 区分或 required-first 顺序的用例删除；其中真实的资源排队、取消、stale candidate、清理和前缀断言保留，按统一行为重写，不能放宽断言或新增 skip。

必须覆盖：

1. 慢 MCP 不阻塞会话打开；用户发送后，initialize 或分页目录读取仍未完成时，实际模型请求数为零。
2. 所有捕获的首次 attempt 结束后才冻结首轮工具；成功候选在其中，失败服务显示具体原因，其余能力正常执行。
3. 超时和发现失败释放等待；后台自动重试立即开始也不会继续扣住首轮。慢 discovery 队列遵循原有资源边界。
4. 等待期间可停止、关闭和修改配置；没有 provider 请求泄漏、锁死、孤儿任务或过期候选采用。取消后再发送仍使用同一 supervisor 的现有事实。
5. 连续执行普通 turn、工具续行、provider retry 时不重复等待。read-only 预览不等待、不消费就绪状态、不安装前缀。
6. 确定性复现“首轮某 MCP 失败，工具续行前重连成功”：两次**最终实际发送**的 SYSTEM/tools 字节完全相同，messages 严格前缀；新工具经 META 可用，原生数组不增加。
7. 独立 cold 恢复、子代理作用域和冻结继承根、显式 compaction successor 各遵守第 3 节；不新增 rebase 路径。
8. 前后端编辑、能力详情、管理交互、插件、CLI 不再暴露或生成服务级 required；Prompt/连接参数的必填行为保持有效。
9. 恢复一个已有 canonical pending 输入、即将建立 cold epoch 的会话，分别阻塞 MCP initialize 和分页目录读取。会话注册、历史及输入框可用；队列只能在注册后开始消费，等待期间实际 provider 请求数和前缀安装次数均为零。释放捕获的首次 attempt 后，重新采集候选并只发送应有的请求；失败则按本规格继续。对恢复的普通排队输入、定时输入和子代理工作验证同一边界。停止当前执行或关闭 Host 后，不得有该输入的 provider 请求漏出；保留或取消其余队列输入遵循既有语义，不得通过重建／删除 pending 行掩盖竞态。

第 9 项必须观察最终 provider 发送边界，不能只用“读取了队列”或“调用了等待函数”代替。若输入使用已冻结的继承根或 compaction successor，另外断言遵循第 3.1 节对应路径，不错误执行 cold 等待或重建根。

真实验收使用保存的生产模型设置，通过现有只读注入和独立本地测试数据库运行；连接凭据不得输出。至少完成一个真实 MCP 的 READY 首轮、一个可控连接失败续行，以及一次真实工具调用后的模型续行。对同一最终请求记录工具数量、v3 估计、provider usage、实际请求次数及逐字节前缀检查；等待期间零模型请求，工具续行恰有其应有的请求，无自动重放。

## 8. 实施顺序

1. 删除配置与投影中的服务级 required，迁移相关夹具及编辑交互。
2. supervisor 统一后台启动；在实际首轮冻结边界接入可取消的首次 attempt 等待。
3. 接入等待进度和失败显示，审计 ROOT、子代理、预览、重连及 compaction 边界。
4. 完成确定性行为测试、真实 MCP/模型验收与全仓残留审计；记录实际 provider 前缀比对证据。

内核资源初始化、关闭约束和注册后激活由上述独立规格负责；本规格负责所有实际执行来源的 MCP 首次等待。两份规格交叉验收恢复 pending 输入，不分别实现两套就绪屏障。

代码及测试按本规格实施并逐条验收；构建安装前显式清理实际配置中的旧服务级字段，不以运行时兼容代替清理。

## 9. 实施与验收结果

配置、协议投影、CLI、插件、前端及 installer Skill 已采用统一首次 attempt 合同；执行边界、注册后激活和等待进度均已接通。服务级 required 没有兼容读取路径。

普通、定时和进程丢失后恢复的 Agent pending 输入均覆盖实际发送边界；初始化／分页发现未结束时请求与前缀安装为零。真实模型验收为 5 个逻辑请求、5 次 SDK attempt、5 次 HTTP；每次均为 36 个内置工具和 31 个 Firecrawl 工具，4 对相邻请求的 SYSTEM/tools 字节一致、messages 严格追加；晚到工具仅经 META 调用。

直接行为用例见 `tests/test_mcp_first_request_readiness.py`、`tests/test_agent_mcp_first_readiness.py` 及定时任务测试。逐条审计和真实请求证据保存在本地 `output/kernel-mcp-implementation/`。本机平台为 macOS Apple Silicon；Ubuntu／WSL 原生环境未在本轮运行。构建安装尚未执行，安装前显式清理旧配置字段的合同不变。
