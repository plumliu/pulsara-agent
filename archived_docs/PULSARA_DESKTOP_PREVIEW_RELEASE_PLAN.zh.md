# Pulsara 桌面预览版 Release 方案

更新日期：2026-10-20

状态：首次 Release 的发行路径已实施。标签流水线生成预览版草稿及安装包；最终下载后的图形界面验收和公开发布尚未执行。本轮只生成草稿，不公开发布。

当前目标是先生成一版可供验收的预览版草稿和安装包。实施范围为移除 AppImage、版本与产物命名、标签构建、Release 草稿、安装说明及最终产物验收；不将数据库 schema、迁移或重置机制的重新设计作为首版发布前置工作。

## 1. 已确定的范围

首版通过 GitHub Releases 发布预览版，仅提供 macOS DMG 和 Linux deb。macOS 暂不申请 Apple Developer 账号，不接入 Developer ID 分发签名或 Apple 公证；以后申请账号后再接入。

| 下载项 | 架构 | 首版平台范围 | 用户安装方式 |
| --- | --- | --- | --- |
| macOS DMG | ARM64 / Apple Silicon | macOS 15+ | 打开 DMG，拖入“应用程序”，从应用图标启动 |
| Linux deb | amd64 / x86_64 | Ubuntu 24.04 | 使用软件安装器或 apt 安装，从应用菜单启动 |
| Linux deb | arm64 / aarch64 | Ubuntu 24.04 | 使用软件安装器或 apt 安装，从应用菜单启动 |

不发布 AppImage、Windows、macOS Intel、RPM、Flatpak 或 Snap。此次实施移除 AppImage 打包目标及其专用运行分支，不保留备用发行渠道。Linux 的平台声明以 Ubuntu 24.04 为基线，不将 deb 格式解释成已支持所有 Debian 系发行版。

基本使用流程为：安装 Pulsara → 配置有效模型连接 → 开始使用。应用启动及内置功能不要求用户预先安装 uv、Docker、Homebrew、编译器或另行启动内核。具体任务所需的软件按下述边界准备。

现有开屏加载状态覆盖内核启动和前端全局初始化：读取界面偏好、bootstrap 和初始会话列表后淡出遮罩，选中会话在后台独立恢复，不阻塞总览、设置或能力页使用；无历史会话时开放新建入口，不自动新建会话，也不等待用户创建会话。不以固定等待时间或页面加载完成代替就绪条件。初始化失败或数据库需要配置时撤去遮罩，显示现有错误或设置入口；后续会话重连不重放开屏遮罩。

开屏由桌面宿主持有一个独立的 `WebContentsView`，原启动文档在工作台导航及初始化期间保持挂载。前端只在首次初始化结束后通过受信任的主框架 IPC 通知宿主退场，不再创建第二层 DOM 开屏页。开屏文档只拥有原有重试、日志和退出等启动操作权限，不具备工作台 IPC 权限；窗口关闭时销毁其 WebContents。

首版不做开发版与发行版隔离：两者默认共用 `~/.pulsara`、桌面单实例和 CLI 入口，验收前须完全退出另一份应用。独立数据验收可使用既有 `PULSARA_HOME`，不新增发行渠道。

首版手动下载安装更新。自动更新、更新服务器、APT 软件源、Homebrew Cask、商店上架和全平台兼容性矩阵均不列入本次范围。

### 1.1 应用自身依赖与任务依赖

| 类别 | 例子 | 交付与管理方式 |
| --- | --- | --- |
| 应用自身依赖 | 内核 Python 及其包、PostgreSQL 及扩展、内置 Chromium、文件搜索工具 | 随安装包交付，由 Pulsara 的构建与更新流程管理 |
| 具体任务依赖 | pandas、项目 npm 包、Node.js、FFmpeg、LibreOffice，以及额外 Skill/MCP 所需的工具 | 按任务检查已有环境，再安装到合适的项目环境或独立工具环境 |
| 操作系统基础 | 受支持系统的基础库、shell、图形桌面等 | 由操作系统提供；deb 所声明的系统依赖由包管理器处理 |

用户可以在对话中让模型准备任务环境。模型通过现有终端工具检查可用命令、解释器和库，在当前权限与用户授权范围内安装缺少的依赖。网络、操作系统兼容性、管理员权限、账号或许可证可能阻止安装；届时说明具体阻碍及需要用户完成的步骤，不承诺任何软件都能自动安装成功。

任务依赖缺失应影响相应任务或扩展能力，不应阻止 Pulsara 启动、基础模型交互及会话保存，也不因此成为所有用户的安装前置条件。

任务环境复用适合的既有项目环境，或按需创建独立环境。不得为完成用户任务而向 Pulsara 安装目录中的内置 Python 安装、升级或卸载包，也不得修改应用内置数据库、浏览器或其他运行资源。项目依赖不写入 Pulsara 自身的依赖声明；应用更新和卸载不顺带管理这些任务环境。

内置 Python 和 Electron 服务应用运行，不自动作为终端中的通用 `python`、`node` 命令。模型不能因为 Pulsara 正在运行就推断用户已安装 Python、Node.js、uv 或其他包管理器；应先检查，再准备任务所需的解释器及工具。

此边界复用现有终端、项目环境和包管理器能力，不新增应用内的通用依赖安装器、全局任务运行时或独立环境管理服务。后续安装说明与相关提示词按此表达，不把任务依赖与内核依赖混写。

### 1.2 已实现的 MCP 连接与 OAuth 桌面返回

- 授权继续使用系统默认浏览器和现有本机回调监听器；MCP SDK 仍负责 OAuth 协议、PKCE 与令牌核验，Pulsara 的现有授权 owner 负责目标确认和凭据保存。只有凭据保存成功，回调页才显示“授权成功”；拒绝、交换失败、目标改变或取消均显示相应未完成结果。回调处理等待进程内完成信号，owner 先发布最终状态再清理监听器，避免处理器与清理互相等待。
- 回调页只保留当前 Pulsara Logo、结果、必要的失败说明和“返回 Pulsara”按钮。使用暖白背景和随内容自适应的浅色圆角卡片，保留紧凑品牌标识、与最终结果一致的状态图标及居中按钮；状态图标上下间距一致，不添加轨道或分隔线；支持深色模式和减少动态效果。Logo 嵌入页面，监听器退出后页面不依赖外部资源；授权码、state、令牌和服务商原始错误不进入页面内容。
- 真实服务多地址连接：HTTPX2 负责 TCP/TLS、连接超时及错误分类；Pulsara 的既有网络策略先校验完整 DNS 答案集，再固定候选 IP 并保留逻辑 Host/SNI。由于 IP 固定替代了 HTTPX 的域名解析，适配层仅在 `ConnectError` / `ConnectTimeout`（HTTP 尚未发送）时尝试同次解析的其余地址；读写失败或已收到 HTTP 响应不得切换地址重放请求。沿用每次连接的现有超时，不增加总寿命上限。
- runtime 复用 HTTPX 的系统及环境代理发现和 `NO_PROXY` 匹配，不提供用户选择开关，也不因启用代理发现而改用环境变量中的证书配置。HTTPS 公网域名的系统解析结果不满足现有网络策略时，使用现有公共 DNS 恢复路径独立取得并校验公网地址，固定实际连接地址并保留逻辑 Host/SNI；不直接接受 TUN/Fake-IP 返回的私网或保留地址，不放开私网校验。此项沿用当前实现，不扩展网络架构或新增发布前置能力。
- 桌面端对用户发起的设备、项目及插件 MCP 登录，复用现有状态读取接口，每秒最多一次串行查询，直到完成、取消、读取失败或工作台退出。状态按原连接归属更新；成功时经受信任 preload IPC 唤回窗口。普通状态查看不抢焦点，注销和新操作取代旧查询，迟到结果不得恢复旧状态。此过程是可丢失的界面观察，不新增持久事件、任务、授权账本或总时长上限，也不自动启用 MCP、重连运行实例或改写 provider 前缀。
- 模型发起的 `AUTHORIZE_MCP` 复用已有根会话工具完成记录作为界面观察入口，只有本窗口新收到的完整、宿主所有的成功结果才触发联动。结果携带原连接的凭据归属、已有配置身份及插件安装身份；前端先向授权 owner 只读核验原连接配置仍然有效并读取它当前的登录状态，再按原设备/项目/插件归属更新登录标签并唤回桌面。不从模型正文判定成功，不重放历史、导入记录或子任务结果；注销、连接删除/更改、会话连接关闭或观察重置后不得根据迟到结果抢焦点。不增加持久事件或授权任务，不再次发起登录或自动重连 MCP。
- `pulsara://oauth/return` 是“返回 Pulsara”的固定应用链接，打包时登记 macOS/Linux 协议处理器，只唤回应用，不接收 OAuth 参数、不宣告授权成功。最终状态始终来自本机授权 owner。用户退出整个应用后未完成的授权不提供跨重启恢复保证。
- 验收覆盖实际回调请求等待令牌交换与保存、交换失败和中途取消；检查桌面状态更新、归属隔离、注销竞态、原生窗口唤回和协议入口。第三方服务商本身的授权需使用其真实客户端配置另行验收。

### 1.3 已实现的能力页 MCP 状态与通知

- 能力页的用户 MCP 配置由当前用户配置 owner 提供；状态与工具目录只读汇总桌面进程内所有已加载、未进入关闭/归档/删除操作的会话，独立于当前选中的会话。检查和配置操作返回的能力快照均使用这一条路径，不接受用于选择能力页运行状态的 `active_session_id` 参数。除会话页及其会话级控件外，其他页面的读取、刷新和可用性均独立于 active 会话。
- 只采用 USER 来源、已有配置身份与当前配置完全相同且 `status_matches_config` 为真的观察；不按同名服务混入项目覆盖、插件来源、旧配置或已脱离当前配置的状态。不恢复冷会话、不新建连接、不改变会话能力或 provider 前缀，不持久化汇总结果。
- 同一配置优先采用可用会话的一份完整观察：READY、DISCOVERING、CONNECTING、FAILED_RETRYABLE、FAILED_TERMINAL、RETIRING、CLOSED、DISABLED 依次优先。同状态优先工具数较多的目录，再比较资源、资源模板、prompt 数；仍相同时按稳定会话 ID 顺序取第一份。状态、工具列表、数量、说明及错误来自同一份观察，不合并不同会话的远端目录。当前配置关闭时显示已关闭；没有匹配观察时显示已配置与空目录。
- 页面进入、恢复可见、窗口恢复焦点或登录状态变化时读取汇总。页面可见期间串行观察：连接、发现或更新中约每 650 ms 读取一次，稳定后每 30 秒读取一次；页面隐藏或退出时停止观察并取消未完成读取。观察不依赖当前会话或模型处理结束。刷新按钮只读重取，显式“重新加载会话能力”仍走原有采纳边界。
- 配置操作的待载入会话数量、重载结果与重试提醒只在操作完成时通过现有 toast 暂态显示，不保留为能力页状态或常驻横幅；普通读取、轮询和重新进入页面不重放操作提醒。
- 全局复用的 toast 支持向右拖动：达到通知宽度 30%（最多 96 px）后自动向右滑出屏幕，未达到则回弹。自动到期和点击关闭复用同一退出动画，动画完成后移除；拖动不触发通知的点击操作，保留键盘操作与减少动态效果偏好。
- Toast 按到达顺序纵向排队：旧通知在上，新通知从底部加入；不重叠，也不因后来通知到达而截掉早先通知。归档会话批量删除提示复用同一队列，进度更新不改变其位置；它不自动到期，点击仍可查看结果，右滑只清除提示，不取消任务，清除后不会因进度更新而重新出现。队列保持底部对齐，下方通知离开时剩余提示平滑下落，复用原节点且不重播入场动画。

### 1.4 已实现的会话执行过程流式展示

- 当前根轮次的流式思考/正文草稿尚无历史分组与窗口身份时，只在展示层续接紧邻的同轮执行过程，复用其顶部 Pulsara 标识。历史缺口、压缩分隔、执行中断、不同轮次及导入记录继续保留各自边界；不为草稿伪造 canonical 历史上下文。
- 执行过程顶部的“正在执行”由整轮活动状态决定，不读取首条已保存步骤的完成状态；思考与工具调用交替时保持显示，确认最终回复或轮次停止后撤去。思考气泡自身的“思考中”仍跟随该思考块，不代表整轮完成。
- 流式正文与最终回复使用相同的换行规则，输出期间预留最终操作行高度。当前根轮次的实时草稿或工具结果提交后，按协议 settlement 的确切 `committed_entry_id` 保留进程内可见内容，直到该记录的分组和正文可显示；它不建立历史读取完整性、执行状态或可分叉资格，重连或进程退出即可丢弃。交接期间只续接同轮、同一已加载窗口中的展示过程，保留历史缺口、压缩和中断边界。附属工具结果的正文读取不撤掉已知调用卡片；结果到达不重建同一卡片，原始结果的异步读取仍按结果记录 ID 隔离。

## 3. 安装包与版本

首个版本为 `v0.1.0-alpha.1`。桌面及前端元数据使用 `0.1.0-alpha.1`，Python 包及 CLI 使用对应的 `0.1.0a1`；源码与 lockfile 在创建标签前一并提交。

每个版本上传三个安装包。以下是建议的对外文件名；架构、版本和平台必须清晰，实际命名优先通过 electron-builder 的配置实现。

| 文件示例 | 用途 |
| --- | --- |
| `Pulsara-0.1.0-alpha.1-macos-arm64.dmg` | macOS 安装包 |
| `Pulsara-0.1.0-alpha.1-linux-amd64.deb` | Linux x64 安装包 |
| `Pulsara-0.1.0-alpha.1-linux-arm64.deb` | Linux ARM64 安装包 |

GitHub 自动提供的 Source code 压缩包是源码，不是安装包；Release 正文直接链接三个安装包，避免让用户自行辨认 Actions 的产物压缩包。

以桌面包版本为发布核对入口。标签去掉 `v` 后须与桌面版本对应；同步核对 Python 包版本、CLI 和应用显示版本。Python 预发布版本按 PEP 440 表示，例如 `0.1.0a1` 对应桌面的 `0.1.0-alpha.1`；deb 的版本编码使用 electron-builder 的既有转换。验证对应关系，不要求不同生态使用非法的同一原始字符串，也不新增版本注册中心。

版本变更及相应 lockfile 更新先提交，再创建标签。构建精确检出标签指向的提交，不在 CI 中临时改版本后冒充原标签内容。

## 4. 发布流程

### 4.1 从标签构建到草稿

1. 发布者选定提交，更新版本及本次更新说明，提交后创建并推送预发布标签。
2. 现有桌面工作流增加标签触发。PR 和日常 `main` 构建继续只做检查及 Actions 产物上传，不创建 Release。
3. 三个原生任务构建并验证 DMG/deb，同一候选提交完成第 8.1 节相关检查。保持 `--publish never`，各架构不自行发布，防止产生只有部分安装包的公开版本。
4. 三个打包任务及必需检查全部成功后，由单一汇总任务下载本次运行的产物，核对版本、架构及三个安装包齐全，创建或更新对应标签的 Release 草稿。汇总只接收本次运行的 DMG/deb，不上传 AppImage 或其他调试产物。
5. 草稿标记为预览版，不设为正式稳定版 latest。发布者从草稿下载同一批产物，完成第 8 节验收后手动发布。
6. 发布后再核对公开下载链接和附件齐全。面向用户的下载入口指向 Release，而非有保留期限的 Actions artifacts。

GitHub 提供草稿、预览版及附件能力，直接复用；不增加发布服务或常驻调度器。[GitHub Release 管理说明](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)

### 4.2 权限与失败处理

构建任务保持仓库只读权限；仅标签触发的草稿汇总任务获得 `contents: write`。PR 不进入发布分支，也不通过有写权限的工作流执行 PR 提供的代码。

任何架构失败或产物不完整时，不自动公开发布。失败原因保留在现有 Actions 日志中，不新增持久化发布任务框架。

同一标签的失败重跑可以修复尚未公开的草稿附件，但必须在重新汇总后重新验收；若需要修改代码，应提交新版本并创建新标签。已公开版本不覆盖安装包、不移动标签，修复以新版本发布。

本轮桌面打包通过不代表其他工作流都通过。发布时记录同一提交的相关检查结果及仍存在的问题；与安装、启动、数据保存或模型执行相关的未解决回归应阻止发布，不能用“预览版”绕过失败断言。

## 5. macOS 未签名预览版

### 5.1 “未签名”的准确含义

本方案中的未签名，指没有 Apple Developer ID 分发签名，也没有 Apple 公证。现有资源搬移后用于本地执行的 ad-hoc 临时签名继续保留；不能为符合字面上的“未签名”而删除 ARM64 二进制运行所需的签名。实施时检查最终 `.app` 的完整性和实际启动行为。

首版不要求开发者证书或 Apple 账号密钥，不新增公证等待任务。后续引入正式签名时，继续对同一桌面应用和嵌套资源处理，不另建一条产品路径。

### 5.2 用户首次安装

Release 正文须在 macOS 下载入口附近写明：

> 此 macOS 预览版尚未使用 Apple 开发者证书签名，也未经过 Apple 公证。首次打开可能被系统拦截。

安装说明保持简短：

1. 下载适用于 Apple Silicon 的 DMG，打开后将 Pulsara 拖入“应用程序”。
2. 弹出 DMG，从“应用程序”打开 Pulsara。
3. 若提示无法验证开发者，在确认文件来自本项目 Release 后，按系统提供的“系统设置 → 隐私与安全性 → 仍要打开”完成该应用的单独授权。

以上为 Apple 官方提供的应用例外打开路径，具体界面以实测系统为准；受管理设备可能不允许设置例外。[Apple 首次打开说明](https://support.apple.com/en-ie/102445)

不把关闭全局 Gatekeeper、关闭 SIP、递归清除隔离属性或重新签名作为常规安装步骤。若正式下载的产物不能通过系统允许的单应用例外打开，先排查打包问题，再据实修订安装说明；不能将开发机直接启动成功写成下载验收成功。

验收必须用浏览器下载 DMG，保留下载带来的隔离属性。不得先清除属性再宣称首次打开通过。

## 6. Linux deb 与 CLI

保留 electron-builder 管理的桌面入口、沙箱与 AppArmor 配置，以及当前 deb 安装/卸载钩子。用户以普通用户运行 Pulsara，提权只用于软件包安装，不以 root 启动应用。

优先说明图形软件安装器；如果桌面没有可用的安装器，提供一条备用命令：

```sh
sudo apt install ./Pulsara-0.1.0-alpha.1-linux-amd64.deb
```

ARM64 用户使用相应的 arm64 文件。命令中的版本随每次 Release 更新，安装完成后从应用菜单启动。

CLI 随应用提供，不要求额外 uv 安装：

- deb 由包管理器维护 `/usr/bin/pulsara`，安装、升级和卸载沿用现有归属检查，不覆盖其他软件的同名命令。
- macOS 安装产物首次启动时沿用现有 `~/.local/bin/pulsara` 注册方式；PATH 未包含该目录或存在旧命令时，沿用设置页的状态和显式重置入口，不修改用户 shell 配置。
- `pulsara app` 启动或聚焦同一桌面应用；管理命令保持原有语义，不引出另一套内核或数据库。

移除 AppImage 时删除 `desktop/package.json` 中的构建目标、CI 的 AppImage 产物上传项、CLI 对临时挂载路径及 `APPIMAGE` 的专用适配、AppRun 参数适配和仅服务这些行为的测试，不保留备用构建开关或兼容分支。`desktop/scripts/linux-cli-entry.cjs` 中提前分派管理命令的包装器也服务 deb，不能整文件误删；保留 deb 无图形环境下运行 CLI、参数及退出码传递的验证，并检查 AppArmor 路径仍对应实际可执行文件。

## 7. 手动更新与数据

用户更新前通过应用的“退出”操作结束 Pulsara，沿用现有关闭路径停止并结算当前工作、回收子进程。macOS 替换“应用程序”中的旧应用，Linux 安装新版 deb。关闭窗口后驻留不等同于已经退出。

安装资源与有效 Pulsara home 分离。普通安装、替换应用、卸载软件包或同版本重启均不主动删除用户数据库及工作文件。

本轮沿用现有数据库初始化、启动和用户确认后的重置行为，不调整 schema、扩展或 PostgreSQL 版本，不设计迁移、备份恢复、`pg_upgrade`、自动回滚或降级支持。数据库版本兼容策略留待后续单独讨论，不作为首次 Release 的新增工程或验收矩阵。

当前桌面重置由 Electron 宿主等待 Python 内核退出后，调用 `BundledPostgres` 核对并处理应用专用目录，后续初始化继续使用现有 Python 数据库 owner。发行工作不修改这条路径，也不因一般启动、权限或连接失败自动清库。

## 8. 适度验收与发布完成标准

### 8.1 CI 保留的检查

三个原生目标继续完成桌面编译与测试、资源搬移验证。Linux 保留 `$ORIGIN`、wheel 相邻依赖及 Pillow 图片读写回归检查，并实际安装 deb，验证 CLI 后卸载。移除 AppImage 专用测试时，保留其与 DMG/deb 共用的有效断言。

桌面 workflow 的独立只读任务执行前端 Vitest、TypeScript 类型检查和 lint，不在三个打包目标重复运行。标签构建以 reusable workflow 调用既有 Ubuntu 后端工作流，对同一标签提交执行两个架构的完整测试及 wheel 隔离安装检查。草稿任务依赖前端、后端和三个打包任务全部成功；其他提交的绿色结果不能替代当前标签验收。

检查每个平台安装包只携带构建资源及所需许可说明，不携带开发机家目录、模型凭据或测试数据库。沿用现有资源及第三方许可收集机制，不新增一套扫描或证据登记系统。

### 8.2 下载产物的实际验收

以当前 macOS 和一个 Ubuntu 24.04 桌面环境完成以下闭环；两种 Linux 架构的原生构建与 deb 检查由已有 CI 覆盖。没有实机 GUI 体验过的架构如实标注，不强制新增设备矩阵。

1. 从 Release 草稿用浏览器下载安装包。macOS 验证第 5 节完整流程，Linux 验证安装与应用菜单入口。
2. 从图标启动，确认不依赖源码 checkout、开发 `.venv`、外部 Python、Docker 或开发机数据库服务。
3. 配置或复用有效模型连接，完成一次包含模型调用、工具执行和文件交付的实际任务；打开右侧文件预览并检查一项可视化。
4. 退出并重开，确认历史存在、交付文件可打开、内置数据库正常启动；验证同版本重启没有清库。
5. 抽查 `pulsara --version`、帮助和 `pulsara app`，确认对应安装产物及同一应用实例。
6. 抽查应用替换及 deb 安装、卸载脚本不会误删用户配置、当前版本数据和工作目录；本轮不扩展到跨 schema 或跨 PostgreSQL 版本升级验收。
7. 结合上述任务抽查依赖边界：在不预先提供开发环境的条件下确认应用可启动及交互，再按需为一个实际任务准备独立环境。确认任务使用该环境，未修改应用内置资源；缺少任务工具时仍可继续普通对话并保存会话。无需为每种第三方工具建立安装测试矩阵。

实际模型调用使用用户同意的有效配置，不将凭据放进 Actions 产物或验收记录。记录系统、架构、版本、结果及已知问题即可，不另建验收平台。

完成标准为：三个安装包及校验文件齐全，相关 CI 通过，实际下载后的安装闭环通过或明确记录尚未覆盖的 GUI 架构，Release 正文与已验证行为一致，最后由发布者公开预览版。

## 9. Release 正文

每次发布只保留用户需要的信息：

1. 版本、预览状态与主要变化。
2. 三个带平台和架构说明的下载链接。
3. macOS 未签名及首次打开步骤；Linux 安装说明。简短说明“配置模型即可开始使用，具体任务需要的软件可在对话中按需准备”，不宣传绝对零系统依赖或任意软件均可自动安装。
4. 配置和工作文件的保存位置，以及更新前需退出整个应用的说明；首版不宣称已提供跨版本数据库迁移能力。
5. 已验证平台、已知问题，以及反馈入口。

预览版不设置为正式稳定版本。下载入口直接指向 Releases 列表或明确版本，不依赖 `/releases/latest` 查找预览版。首次实施时补齐下载与安装所需的用户文档；不以全面重写历史文档或 README 为前置工作。

## 10. 实施顺序与语义边界

| 顺序 | 变更 | 验证重点 |
| --- | --- | --- |
| 1 | 移除 AppImage 构建目标及专用运行代码 | DMG/deb、CLI、沙箱与 AppArmor 共用行为完整保留 |
| 2 | 确定版本规则、产物命名和标签触发 | 标签、应用、CLI 与软件包版本对应 |
| 3 | 补齐前端检查，增加成功后汇总至 Release 草稿的任务 | 同一提交的必需检查通过，三个产物齐全，权限最小，不自动公开、不覆盖已发布版本 |
| 4 | 补充简洁安装及更新说明 | 未签名行为、平台范围、退出更新与数据保存说明准确 |
| 5 | 下载验收并人工发布预览版 | 验收的是最终附件，公开后下载入口可用 |

electron-builder 负责安装包和平台集成，GitHub Actions/Release 负责构建运行、附件与发布状态，Pulsara 继续拥有原有宿主、内核及专用数据库生命周期。新增内容限于发行配置和必要的小型适配。

不改变 provider 输入前缀、模型上下文、任务调度、工具执行、会话持久化及关闭结算语义，不增加运行时 durable event、job、恢复协议或兼容路径。发行失败通过现有 CI 和草稿处理，不能扩展成应用内的执行恢复机制。

本文件记录已实现的发行路径和公开前验收要求。本轮允许创建标签、构建安装包及创建或更新预览版草稿，不允许公开发布；不执行清库或改造数据库。
