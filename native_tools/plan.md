# Pulsara Plan 工具合同与使用教程

共用规则见[原生工具修订草案索引](../archived_docs/PULSARA_NATIVE_TOOL_CONTRACTS_AND_TUTORIAL_DRAFT.zh.md)第 1、2 章。

状态：当前生效合同。本族仅提供 ROOT 原生工具，不提供 JS API。当前记录 enter_plan、ask_plan_question、exit_plan 的参数、业务返回值、原生用法及下述共同等待期限。

Plan 提问和方案审批统一使用 **10 分钟**交互等待期限，从交互被接受进入等待时计时，不因页面刷新、重连或 steer 重置。到期仍未决时直接取消并关闭弹窗，结束本次等待。补充输入仍沿统一安全点语义排队，不提前取消交互；真实回答、审批决定和到期结算沿既有事务规则确定唯一结果。

- ask_plan_question 超时：结束本次提问，以 CANCELLED 和 content 中的“问题等待回答超时（10 分钟），未获得用户回答。”结算，原只读计划轮继续；不伪造答案，不自动重开弹窗。模型可据此决定后续规划，需要退出时自行调用 exit_plan，runtime 不因提问超时自动退出整个规划。
- 方案审批超时：直接取消并关闭审批卡，以本次 exit_plan 的唯一最终工具结果返回 CANCELLED，content 明确“方案审批等待超时（10 分钟），未获得用户批准。”。结束本次等待，当前只读轮继续；规划仍保持活动，由模型决定是否自行调用 exit_plan 退出，不自动批准或启动实现续接，也不声称用户主动取消。

enter_plan 本身不等待用户答复，不适用这项期限；该期限不限制整个规划任务或工作流的累计时长。

本轮运行信息和规划相关 observation 统一遵循[Runtime Observation 修订草案](../archived_docs/PULSARA_RUNTIME_OBSERVATION_REVISION_DRAFT.zh.md)第 1.3、6 节：所有新 turn 首次输入、用户主动 steer 及活动 turn 压缩后的恢复说明按各 source 规则发送。Runtime 交接专指压缩后的 TODO／PCA 状态交接，Plan 自动续接属于新 turn 的开始。环境、权限、时间合为 TURN_CONTEXT；PLAN_MODE 只在活动规划 turn 压缩后说明状态，并附进入规划前 turn A 最后一条已交付真实用户消息／steer 的完整原文，标为“进入规划前的用户输入”；APPROVED_PLAN 在批准后的执行续接 turn 携带完整获批原文，并随该执行 turn 的压缩恢复承接。每类独立使用 source／body 块，压缩后与 TODO／PCA 并列，不在普通规划过程中重复追加状态提示。runtime 自动续接按新 turn 规则，在准备汇报时比较 Skill／MCP 最新相关状态快照与上次已告知快照，临时计算最新净 diff，有相关变化才通知；输入安装成功后，用生成本次通知所依据的状态快照替换上次已告知快照，安装失败保留旧快照。通知侧只保存上次已告知快照，diff 用完即可丢弃，准备消息后再发生的变化留待下一次比较。不冒充用户输入触发 slash 激活或记忆观察。合法冷上下文及采用的压缩 successor 按 Skill 完整目录、轻量 MCP 服务目录、压缩交接手册的顺序建立初始能力区域，并从各自冻结事实初始化比较快照。Plan 普通新 turn 本身不重发完整目录；初始目录不属于 TODO／PCA 或 runtime observation，具体遵循[MCP 初始目录规范](../archived_docs/PULSARA_MCP_CATALOG_INCREMENTAL_IMPLEMENTATION_SPEC.zh.md)。

## 1. enter_plan：进入计划模式

### 1.1 用途与行为

进入只读计划模式，围绕已有对话中的任务进行调查、讨论和规划。进入本身不等待用户确认，也不表示计划已经获批。

| 当前状态 | 成功后的行为 |
| --- | --- |
| 尚未进入计划模式 | 创建计划工作流，结束当前轮，并自动开启只读计划轮继续处理已有任务 |
| 已处于计划模式 | 保持当前工作流和当前轮，成功返回，不重复创建工作流或后继轮 |

保持现有权限和交接语义：只读计划权限在自动后继轮生效，不修改原轮已冻结的权限。模式切换及自动继续仍由既有 Plan owner 处理，不因公开返回值精简而删除实际控制关系。

只读规划新 turn 首次输入提供其环境、时间和冻结权限的 TURN_CONTEXT。模型从 enter_plan 调用及结果得知已进入规划，不另发进入或持续规划的 PLAN_MODE。该只读 turn 内发生压缩时，在 TODO／PCA／待读 Skill 旁恢复 TURN_CONTEXT 和独立的 PLAN_MODE 块；即使这些交接对象为空，也不省略运行说明。PLAN_MODE 明确“当前仍处于计划模式”，并附进入规划前原 turn A 最后一条已交付真实用户消息／steer 的完整正文；没有对应输入时只说明状态，不伪造引文。规划 turn B 连续压缩时承接同一份进入前原文；B 内后续补充仍按正常顺序生效，不以旧引文覆盖后来的要求。该信息从已有输入和运行事实投影，不要求新增工具参数或另存一份正文。

已结束 turn 的空闲压缩不提供 Runtime 交接，也不生成当前规划或执行要求。后续任何来源开启新 turn 时，首次模型输入都必须发送 TURN_CONTEXT，提供新 turn 的环境、时间和冻结权限，并检查 Skill／MCP 相关净变化；记忆仍按真实用户输入的独立规则处理，不继承旧轮冻结权限。能力通知在既有 provider 输入安装成功时，用生成本次通知所依据的状态快照替换上次已告知快照。

必须作为该响应中唯一的工具调用。同一响应若还包含其他调用，仍沿现有批次屏障处理，其他调用不执行；不因 enter_plan 参数错误或不可用而放行其余调用。

### 1.2 参数

无参数，只接受空对象 `{}`。删除公开 reason 参数及对应校验，不接受 null 或额外字段。任务目标继续来自已有对话，不要求模型再次填写。

```text
工具：enter_plan
参数：{}
```

### 1.3 返回值

业务结果只保留 meta 和 content，不返回业务 target：

| 字段 | 含义 |
| --- | --- |
| meta.status | SUCCESS、ERROR 或 CANCELLED，沿共用调用状态规则 |
| content | type:text、value:string 的有序文字项数组，简短说明本次结果 |

| 情况 | 状态 | content 说明 |
| --- | --- | --- |
| 首次成功进入 | SUCCESS | 已进入计划模式。 |
| 重复进入 | SUCCESS | 当前已处于计划模式。 |
| 调用失败 | ERROR | 实际失败原因；不声称已进入计划模式 |
| 调用取消 | CANCELLED | 实际取消情况及必要的已知事实 |

删除正文中的 status 和 plan_control，不另加控制枚举、meta.error、_hint、workflow ID 或 Plan Target。具体错误和必要已知事实直接写入 content；没有产生业务结果的早期失败沿既有错误通道报告，不伪造结果。

保存的业务值示例：

```json
{
  "meta": {"status": "SUCCESS"},
  "content": [
    {"type": "text", "value": "已进入计划模式。"}
  ]
}
```

### 1.4 原生交付示例

首次成功进入：

```text
observed_at_utc: <实际观察时间>

meta:
  status: SUCCESS

content:
  已进入计划模式。

tool_result: <完整结果的导出 Target>
next: null
```

实际取得的 observation_duration_microseconds 与上述字段顶层并列；未测得时不伪造为 0。重复进入使用相同包装，content 改为“当前已处于计划模式。”。

例如携带已删除的 reason 参数时，错误正文可以简短说明：

```text
meta:
  status: ERROR

content:
  enter_plan 不接受 reason；请使用空对象 {}。
```

上例只摘出错误状态和说明。确实产生并完整保存的错误业务值仍沿共用规则交付，正常交付完毕可返回其 tool_result 和 next:null；保存或交付失败不得冒充正常完成。

完整结果保存、原生 12k 分页及 NEXT 续读均沿统一交付规则，不为 Plan 增加独立协议。结果较短时第一页即完整结果；补读和导出不再次进入计划模式，也不重复启动后继轮。

## 2. ask_plan_question：等待用户回答

### 2.1 用途与行为

在活动的计划模式中提出一个需要用户决定的问题。调用由 ROOT 单独发出，其他同批调用沿既有 Plan 屏障处理，不执行。本工具不提供 JS API。

问题被接受后显示交互卡片，等待用户选择或提交自由回答；收到回答或发生第 2.4 节的超时取消后，工具结果交给模型，原只读计划轮继续。等待期间不反复调用模型。

普通发送和显式 steer 均保持现有统一安全点语义：输入可以入队，但不自动关闭问题、不代答；本次问题结算后，模型先收到工具结果，再按序处理待交付的补充。Stop、强制退出、关闭等显式控制仍沿各自既有生命周期处理，不伪造尚未产生的工具结果。

### 2.2 最简参数表

| 参数 | 类型 | 必填与默认 | 明确含义 |
| --- | --- | --- | --- |
| question | string | 必填，非空 | 一个完整问题及必要上下文；保持现有 16 KiB UTF-8 边界 |
| options | 选项对象数组 | 可选，默认 [] | 省略或空数组表示开放问题；提供选项时为 2～3 个，按给定顺序显示 |

每个选项保留以下字段：

| 字段 | 类型 | 必填与默认 | 明确含义 |
| --- | --- | --- | --- |
| label | string | 必填，非空且各选项之间唯一 | 选项文字，保持现有 256 字节 UTF-8 边界 |
| description | string | 可选，默认空字符串 | 选择的影响或取舍，保持现有 2 KiB UTF-8 边界 |
| recommended | boolean | 可选，默认 false | 是否推荐，最多一个选项为 true；不代表用户已经选择 |

只接受 question、options 及上述选项字段，不接受 null 或额外字段。删除 allow_free_text 参数及其分支校验；有无选项都始终允许自由回答，不要求模型填写“其他”选项。模型不填写选项 ordinal、工作流或 interaction ID。

### 2.3 返回值

业务结果只保留 meta 和 content，不返回业务 target：

| 字段 | 含义 |
| --- | --- |
| meta.status | SUCCESS、ERROR 或 CANCELLED |
| content | type:text、value:string 的有序文字项数组，保存回答或实际失败／取消原因 |

| 情况 | 状态 | content |
| --- | --- | --- |
| 用户选择选项 | SUCCESS | 用户选择：<所选 label> |
| 用户提交自由回答 | SUCCESS | 用户实际提交的完整回答，保留换行，不概括或改写 |
| 等待满 10 分钟仍未获得回答 | CANCELLED | 问题等待回答超时（10 分钟），未获得用户回答。 |
| 调用失败 | ERROR | 实际失败原因，例如当前没有活动的计划模式或参数无效 |

删除公开的 plan_control、answer 包装、answer.kind、选项 ordinal、cancelled_by、interaction ID 及重复状态。选择结果用文字表达，不重复返回选项说明；内部仍保留确认实际选择和结算所需的控制事实。错误不增加 meta.error、_hint 或另一组错误分类字段。

例如用户提交自由回答，保存的业务值是：

```json
{
  "meta": {"status": "SUCCESS"},
  "content": [
    {"type": "text", "value": "先只改存储，编辑行为以后再讨论。"}
  ]
}
```

### 2.4 十分钟超时取消

使用本文件开头的统一 10 分钟期限，到期仍未获得回答时直接取消并关闭问题卡片，结束该次等待并返回 CANCELLED。超时是一种明确的取消情况，不新增 TIMEOUT 状态或超时字段；content 明说未获得用户回答，不写成“用户取消了问题”。

超时不自动选择推荐项，也不构成批准或授权。原只读计划轮继续，由模型判断是否还能规划、如何处理已排队的补充，以及是否自行调用 exit_plan 退出。runtime 不自动退出规划、不自动重新发起同一提问。

回答与超时由现有 Plan 结算事务确定唯一结果，已接受的真实回答不改写成超时；超时结算后到达的回答不覆盖原结果。分页补读不重开交互或重新计时。

### 2.5 原生调用与结果示例

带选项的问题：

```text
工具：ask_plan_question
参数：
  question: "此次改造是否保留现有文件编辑行为？"
  options:
    - label: "保留现有行为"
      description: "仅调整存储和返回形式。"
      recommended: true
    - label: "同时调整编辑行为"
      description: "一并修改编辑规则。"
```

用户选择第一项后，原生结果为：

```text
observed_at_utc: <实际观察时间>

meta:
  status: SUCCESS

content:
  用户选择：保留现有行为

tool_result: <完整结果的导出 Target>
next: null
```

用户也可直接填写“先只改存储，编辑行为以后再讨论。”，此时使用同一包装，content 为这段实际回答，不增加 answer 类型字段。实际取得的微秒耗时仍按共用规则顶层并列；未知时不伪造为 0。

开放问题只传 question：

```text
工具：ask_plan_question
参数：
  question: "你希望这个页面优先解决什么问题？"
```

等待超过十分钟仍无回答时，原生取消结果为：

```text
observed_at_utc: <实际超时结算观察时间>

meta:
  status: CANCELLED

content:
  问题等待回答超时（10 分钟），未获得用户回答。

tool_result: <完整取消结果的导出 Target>
next: null
```

此处 next:null 表示取消结果已交付完，不表示问题已经获得回答或计划获批。模型如决定结束规划，另行调用 exit_plan；本次取消结果保持不变。

例如携带已经删除的 allow_free_text 时，错误说明可为：

```text
meta:
  status: ERROR

content:
  ask_plan_question 不接受 allow_free_text；自由回答始终可用。
```

错误示例省略通用观察和交付字段。实际存在的完整业务结果仍完整保存，原生按统一 12k 规则交付；tool_result、next、保存失败及交付失败均沿共用规则，不为本工具新增续读协议。

## 3. exit_plan：提交方案审批或无方案退出

### 3.1 用途与分支

在活动的计划模式中单独调用。非空白 plan 提交完整方案并阻塞等待用户审批；省略或空白 plan 则直接退出规划，不创建审批卡。两条分支均沿现有 Plan 批次屏障处理，同响应中的其他工具不执行。

| 分支 | 调用期间的行为 | 返回与后续运行 |
| --- | --- | --- |
| 提交方案审批 | 保留本次方案参数，尝试写出 Markdown，打开审批卡；原规划轮等待本次调用，不因打开卡片就结束 | 用户决定或十分钟超时后，只返回一次最终工具结果，再按第 3.4 节结算规划及续接 |
| 无方案退出 | 不等待审批，不创建审批卡或方案文件 | 返回退出结果，结束规划及当前轮，自动开启后继轮，按进入规划时保存的权限继续用户任务 |

打开审批卡仅表示交互已经进入等待，不先返回“已提交审批”的 SUCCESS 工具结果，不生成等待页或 NEXT。等待期间不反复调用模型，普通补充仍沿统一安全点语义入队；本次调用按实际决定或超时结算后再处理相应后续输入。无方案退出不代表此前的草案获批，也不把未批准的草案自动作为执行要求。

已开放审批时，将队列消息明确用作方案修订的入口仍提交 REVISE 决定，结算本次审批；完整反馈沿第 3.4 节的用户输入路径交付。它不等同于普通 steer，不自动批准方案。

### 3.2 最简参数表

| 参数 | 类型 | 必填与默认 | 明确含义 |
| --- | --- | --- | --- |
| plan | string 或 null | 可选，默认省略 | 非空白文字为完整方案；省略、null、空字符串或纯空白字符串均表示无方案退出 |
| summary | string | 可选，省略或空白时使用默认文件名方案.md | 方案文件的简短标题，仅用于命名 Markdown，不是额外展示摘要 |

只接受 plan、summary，不增加 mode、文件 Target 输入或输出路径参数。summary 不决定分支，无方案退出时不用于创建文件。提交方案仍由模型在 plan 参数中提供完整文字，不要求提前创建文件。

plan 为字符串时保持现有 1 MiB UTF-8 输入边界；其他类型、未知字段及超出边界的字符串均拒绝，包括超出边界的纯空白字符串。空白判断仅选择分支，非空白方案保留原始文字和换行，不 trim、不补末尾换行、不添加标题或 front matter。

该边界针对 plan 原文，不扣除后续 observation 的提示和消息包装。APPROVED_PLAN 按包含完整原文、JSON 转义、提示及实际封装的真实请求计费；删除其沿用旧单 source 1 MiB 等载体字节门槛的限制，不截断原文、不改摘要、不缩小本节原有输入范围，也不另设替代限额。最终完整请求仍按实际 provider 输入和真实资源边界准入，真实失败如实报告。

### 3.3 数据库与 Markdown 两份保存

提交审批时，数据库保留方案参数，并尝试另存 Markdown；两份内容的用途如下：

| 位置 | 保存内容及用途 |
| --- | --- |
| 数据库中的本次工具调用参数 plan | 保留原始方案，审批记录引用对应调用，审批和执行续接均使用该次保存内容；不另建独立方案正文副本 |
| 会话工作区根目录 .pulsara/plans/ 下的 Markdown | runtime 尝试将同一 plan 原文按 UTF-8 自动写出，供用户及模型通过 read_file 回看；写入失败不阻止数据库审批，原因进入最终结果的 content |

数据库 hardcut 后仍由共同调用内容项保存 plan 参数，不要求为方案另加 text 项或另一份完整业务 JSON。Markdown 是本工具明确允许的额外文件产物，不因正文统一而删除，也不扩展为其他工具的自动文件镜像。

目录由 runtime 按需创建，以会话工作区根为准，不随终端命令中的 cd 改变。使用模型提供的 summary 作为文件名标题，按本地文件名规则处理并使用 .md 后缀，不将 summary 解释为路径；省略或空白时使用方案.md。重名时按“方案 (2).md”“方案 (3).md”顺延，其他标题使用相同规则，不使用短哈希或另造命名身份。新的提交不覆盖已有文件，同一提交的确认复用实际已保存的路径，不重新编号或创建新文件。

写文件是 exit_plan 内部的固定职责，不要求模型或用户预先调用文件工具，也不开放只读规划阶段的一般文件写权限。输入仍是 plan 全文，不改为读取文件 Target。

审批和执行不回读 Markdown 来替换已保存参数，文件后续变化不自动修改已提交或已批准的方案。修订后通过新的 exit_plan 调用提交完整替换方案，并产生新的文件；取消或超时不自动删除已写出的方案文档。

### 3.4 唯一最终结果与续接

业务结果使用以下字段：

| 字段 | 提交方案审批分支 | 无方案退出分支 |
| --- | --- | --- |
| target | Markdown 完整保存成功时返回顶层 PATH Target，包括最终取消或超时的情况；文件保存失败则省略 | 省略，不创建或伪造文件 Target |
| meta.status | 按下表表达实际审批处理结果，不以提交成功或文件保存成功提前返回 SUCCESS | SUCCESS 表示本次退出成功；失败或取消沿共用状态规则 |
| content | type:text、value:string 的有序文字项数组，简短说明实际决定或超时；修订反馈另沿用户输入路径交付，有文件写入失败时一并说明原因 | 简短说明已退出及实际恢复的权限 |

| 审批等待的结束原因 | 最终 meta.status | content 与后续运行 |
| --- | --- | --- |
| 用户批准 | SUCCESS | 说明用户已批准及实际恢复的权限；结束规划及原轮，自动创建执行续接，使用数据库中的本次完整方案 |
| 用户要求修订 | SUCCESS | 简短说明“用户要求修订方案。”；当前只读轮继续，接收完整反馈，由模型继续规划、提交替换方案或自行退出 |
| 用户取消审批 | CANCELLED | 说明用户取消了本次审批；结束本次等待，当前只读轮继续，由模型决定是否退出规划 |
| 十分钟仍未决 | CANCELLED | 说明“方案审批等待超时（10 分钟），未获得用户批准。”；直接关闭审批卡，当前只读轮继续，由模型决定是否退出规划，不自动批准或启动执行续接 |
| 实际处理失败 | ERROR | 实际失败原因及已知效果，不伪造用户决定或文件 |

每次调用只关联一份最终工具结果。等待审批的 OPEN 交互可以没有结果；用户决定或超时后再保存并交付最终值，不预先保存提交成功结果再改写，也不补发第二个结果。内部仍保留实际决定、来源、权限恢复和续接所需的控制事实，不因公开字段减法丢失它们。

修订、取消审批和超时均保持同一工作流 ACTIVE、原轮 RUNNING 及其冻结的只读权限；最终工具结果交给该轮下一次模型调用，不只是保存或展示给用户，不创建只读修订后继轮。只有批准或无方案退出才结束规划及原轮、恢复进入规划时保存的权限并自动续接。显式停止、强制退出和关闭会话仍按各自控制语义处理，取消一次审批不等于停止任务。

批准后自动开启的执行 turn，首次输入包含其实际恢复权限的 TURN_CONTEXT，以及一份独立 APPROVED_PLAN observation：直接投影数据库中本次批准的完整 plan，并提醒“部分工作可能已经完成，请结合已有进展继续，避免重复执行。”该 turn 后续压缩时，在 TODO／PCA 旁再次提供 TURN_CONTEXT 和完整 APPROVED_PLAN 原文及提醒，不依赖模型摘要，也不构成再次批准或重新执行。无方案退出提供新 turn 的运行信息，不生成 APPROVED_PLAN，不将旧草案作为获批内容。这些新 turn 也按统一规则检查 Skill／MCP 相关净变化；不触发用户 slash 激活或记忆观察，不改变既有审批和执行结算。

无论原始 exit_plan 调用是否仍在近期历史中，都按上述时机提供完整 APPROVED_PLAN，不受旧“历史里已有原文就跳过”及其 pin／materialize 展示分支影响。原始调用与结果仍按正常规则保留，不为去重删除历史；完整计划沿既有关联提取，不另存一份方案正文。

修订反馈沿已有用户输入路径完整交付一次，保留有序文字、图片、批注／引用及其真实来源和图片读取资格，支持纯图片反馈。先交付本次最终工具结果，再在安全点按已有输入顺序处理反馈及已接纳补充；不把反馈正文复制进工具 content 或 Plan 控制 JSON，不另建反馈正文实体或追溯映射，也不因修订重排已有上下文。普通 steer 仍只是排队补充，不替代回答或审批决定。

数据库约束与触发器须匹配上述生命周期：OPEN 的 DRAFT_REVIEW 属于 RUNNING 原轮，且可无 control_tool_result_id；结算为 APPROVED、REVISION_REQUESTED 或 CANCELLED 时允许该关联从空值写为唯一最终结果。取消“DRAFT_REVIEW 一律要求原轮 COMPLETED”及“REVISION_REQUESTED 必须关联 decision_continuation_entry_id”的旧约束；修订、取消和超时不填写该后继关联，批准仍关联实际执行续接。保留调用、会话、工作区、结果的精确归属及已结算结果不可改写的约束，实施时同步调整当前合同测试，不增加字段或状态。

保留实际存在的顶层 target，作为返回后最直接可读的方案文件引用，不在 content 里重复相同 Target。content 不回传方案全文，不并列返回 summary 或另存展示摘要。公开状态只有 SUCCESS、ERROR、CANCELLED，删除公开的 plan_control、正文 status、workflow ID、interaction ID 和单列的 resume_permission_mode；权限等必要事实用简短文字表达。

Markdown 写入失败不阻止等待审批，也不单独改变用户决定或超时对应的最终状态；在最终 content 中说明原因，省略未保存文件的 PATH Target。审批超时和用户决定沿现有事务规则确定唯一结果，已接受的决定不改写；已结束交互不接受迟到决定。

有文件时，PATH Target 指向方案文件；原生 tool_result 指向本次最终的简短工具结果，next 只补读该结果。导出 tool_result 不等于导出方案全文，读取方案文件使用实际返回的 PATH Target。NEXT 不等待新的审批决定、不重开卡片或重置期限，也不重复模式切换及自动续接。

例如用户批准后，保存的最终业务值为：

```json
{
  "target": {"kind": "PATH", "path": ".pulsara/plans/文件工具改造.md"},
  "meta": {"status": "SUCCESS"},
  "content": [
    {"type": "text", "value": "用户已批准方案，恢复 accept-edits 权限并继续执行。"}
  ]
}
```

### 3.5 提交方案审批的原生示例

```text
工具：exit_plan
参数：
  summary: "文件工具改造"
  plan: |
    # 文件工具改造方案
    1. 统一读取和写入的返回结构。
    2. 保留原始换行。
    3. 完成相关验证。
```

此时打开审批卡，模型等待，不先返回成功结果。以下假设文件保存成功、进入规划时保存的权限为 accept-edits，且用户批准：

```text
observed_at_utc: <实际审批结算观察时间>
target: {"kind":"PATH","path":".pulsara/plans/文件工具改造.md"}

meta:
  status: SUCCESS

content:
  用户已批准方案，恢复 accept-edits 权限并继续执行。

tool_result: <本次最终结果的导出 Target>
next: null
```

若用户要求修订，则最终状态为 SUCCESS，content 为“用户要求修订方案。”；例如用户提交“先只统一返回结构，不调整编辑行为。”及一张图片，实际反馈作为有序用户输入交给当前只读轮，不重复写进工具结果。纯图片反馈也保留真实图片，不以一句文字代替。若用户主动取消本次审批，则状态为 CANCELLED，content 说明取消，当前只读轮继续。它们与批准、超时互斥，不是对一份先前成功结果的更新。

十分钟到期仍未决时，直接关闭审批卡，返回本次调用唯一的取消结果；以下仍假设文件保存成功：

```text
observed_at_utc: <实际超时结算观察时间>
target: {"kind":"PATH","path":".pulsara/plans/文件工具改造.md"}

meta:
  status: CANCELLED

content:
  方案审批等待超时（10 分钟），未获得用户批准。

tool_result: <本次取消结果的导出 Target>
next: null
```

文件已经存在，因此取消结果也可以提供 PATH Target；这不表示方案获批。next:null 只说明取消结果已经交付完。该结果交给当前只读轮继续处理，模型可继续规划或自行调用无方案 exit_plan；runtime 不因审批超时自动退出规划。

若 Markdown 因工作区不可写而保存失败，审批仍正常进行。例如之后用户批准时，最终结果不带 PATH Target：

```text
observed_at_utc: <实际审批结算观察时间>

meta:
  status: SUCCESS

content:
  用户已批准方案，恢复 accept-edits 权限并继续执行。
  Markdown 文件保存失败：工作区不可写。

tool_result: <本次最终结果的导出 Target>
next: null
```

若同时是审批超时，则最终状态仍为 CANCELLED，content 同时说明审批超时和文件写入失败，不因写文件失败冒充用户批准。

有返回的 PATH Target 时，模型可通过文件工具回看：

```text
工具：read_file
参数：
  target: {"kind":"PATH","path":".pulsara/plans/文件工具改造.md"}
```

这次读取沿 read_file 合同，原生按 12k 分页；读取或补页不重新提交审批。省略 summary 时依次使用方案.md、方案 (2).md 等；同名“文件工具改造.md”已存在时，本次文件可为“文件工具改造 (2).md”，实际路径以返回的 target 为准。

### 3.6 无方案退出的原生示例

最简调用：

```text
工具：exit_plan
参数：{}
```

传入 plan:null、空字符串或纯空白字符串使用同一分支。以下假设进入规划时保存的权限为 accept-edits：

```text
observed_at_utc: <实际观察时间>

meta:
  status: SUCCESS

content:
  已退出计划模式，恢复 accept-edits 权限并继续处理任务。

tool_result: <本次退出结果的导出 Target>
next: null
```

此分支不等待审批，不创建 .pulsara/plans 目录或 Markdown，不返回 PATH Target。恢复权限来自工作流进入时保存的值，不使用当前规划轮的只读权限或输入框此刻选择的权限；原轮已冻结的权限不改写。

ask_plan_question 超时后，模型也可以按此方式自行结束规划；runtime 不将提问超时直接转换为该工具调用。

### 3.7 失败、取消与交付边界

没有活动规划、参数无效或审批／退出处理失败时，沿实际结果使用 ERROR；取消沿共用规则使用 CANCELLED。Markdown 保存失败不阻止审批，也不单独覆盖最终状态，失败原因进入最终 content，不返回假路径。不增加 meta.error、_hint 或另一套控制状态。

请求已进入审批等待不等于工具已成功返回，最终结果在用户决定或十分钟超时后产生。若文件已经完整写出，但确认审批请求接纳失败，则说明文件已保存、审批未提交；实际可读时可以返回其 PATH Target，不因整体失败声称文件不存在。

审批提交或决议应答丢失、状态不确定时，沿既有确认路径查询原操作；仍无法确定就如实说明状态未确认，不宣称未提交或未决议，不重新提交、重做决定或另造文件。

后续结果保存或交付失败时，保留实际已经发生的审批决定、退出或文件写入事实，沿统一交付规则报告，不重复写出新文件、不重复创建审批或后继轮。早期失败没有实际业务结果时，不为填满包装而伪造结果。

原生观察时间和实际存在的微秒耗时保持顶层。完整结果保存、12k 分页、tool_result、NEXT 及导出使用共用规则，不为本工具增加独立分页协议或持久恢复机制。本节不授权修改生产实现。
